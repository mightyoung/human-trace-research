# 属性索引 v3：组合筛选 + 能力闸门（2026-11-12）

> 上游：`docs/mainline-attr-index-2026-11-11.md`（索引怎么建、承诺边界）
> 、`docs/mainline-attr-multiframe-2026-11-12.md`（多帧投票封顶，为什么不再刷指标）
> 本文只讲产品侧收口：**从「单字段筛选」做到「多条件检索 + 不可判显式化 + 结果可导出」**。

## 结论先行

索引页现在支持 **AND 多条件检索**（每条件独立置信度门），并且 **按能力矩阵做闸门**：
某字段在实体所属框高档位上 `level='n/a'` 时，既不参与筛选也不显示在卡片上，
被挡住的数量在统计行单独报出。这修掉了一个会直接误导决策的缺陷——
**673 个实体 × 9 个字段全部有值**，S 档也能筛出「背包=是」，与同一页面上的能力矩阵自相矛盾。

同时把**置信门的静默丢弃**也修了：默认门从 .70 落到 .60（「黑衣女」21 人，.70 只能查到 5 个），
被置信度挡掉的实体单独报数，页面上「匹配 9 · 另有 12 个置信度没过门」，
9+12=21 账目完整。**查不到 ≠ 没有**，这句话在这页上必须能验证。

最后把**「看到」变成「能带走」**：全部命中可导 CSV / 截图包（页面只显示 60 条，导出不受分页限制），
且导出与查询共用同一套筛选参数 —— 名单不会因为换了个入口就变。

卡片也从「一张图 + 一个帧数」变成**点得开的实体画像**：时间段、带黄框的 16:9 环境帧、
时间段均分的 5 张时间线帧、以及从原片同一时刻起播的播放器。**判人不再靠一帧**。

## 一、修掉的缺陷：筛选不认能力矩阵

| | 改前 | 改后 |
|---|---|---|
| S 档筛「下装颜色=黑」 | 返回实体，置信度 0.99 | **0 条**，并报「85 个因档位能力不足被排除」 |
| S 档下装颜色的取值下拉 | 黑 9 / 白 12 / … | **空**（该字段在 S 档不可判，不给假选项） |
| 筛「背包=是」 | 11 条（含 M/S 档） | **8 条**（3 条 M/S 档被挡） |
| 卡片 | 只显示可信字段，其余静默消失 | 多一行「不可判（M 档）：背包 · 拎东西」 |

为什么是缺陷而不是取舍：`capability` 一直在接口里，也一直在页面上以表格展示
（S 档下装两字段写的是「不可判」），但筛选逻辑完全没读它。**同一个页面上，
表格说不可判、结果却给结论。**

## 二、组合筛选：语义与两个设计决定

### 2.1 AND 语义，逐条件置信度

`GET /api/attr/index?conds=[{"f":"top_color","v":"黑","conf":0.7},{"f":"glasses","v":"是","conf":0.8}]`

- 条件是 **AND**；每条件自带 `conf`，不再共用一个全局阈值；
- 取值留空 = 「该字段有结论即可」（用于「只看能判出性别的人」这类筛选）；
- 同一字段只允许一条条件（`上衣=黑 且 上衣=白` 恒为空，前端写入时直接去重）；
- 旧参数 `field`/`value`/`min_conf` 保留，`conds` 优先 —— 老链接和老脚本不用改。

### 2.2 分面计数改成「cross」语义

第一个条件选完，第二个下拉里的数字要反映**还剩多少人**，否则用户会一直撞空。

★ 分面把**该字段自身的两道门**也算进去：其他条件 + 本字段的置信门。否则会出现
「下拉写 91、点下去 90」这种自己打自己的数——`上衣颜色=黑` 之后开「戴眼镜」，
下拉给 `任意取值 106 / 是 98 / 否 8`，选「是」就正好是 98 条。账对得上才敢让用户照着数字做判断。
要退回旧口径（全库计数）传 `facet_mode=base`。

**0 命中的取值不隐藏，只置灰**：`戴帽子=是` 全库只有 16 人且都是白上衣，
选完帽子再看上衣颜色，10 个颜色是 0——列出来写「（0）」并禁用，
比让选项直接消失好：后者会让用户以为「这个字段不能用」。

### 2.3 空结果给诊断，不给「没有匹配」

同时满足全部条件为 0 时，后端逐个「去掉一条」重算，返回 `drop_one`：
`[{去掉戴帽=是 → 103}, {去掉黑上衣 → 16}]`，前端渲染成可点按钮，点一下即删除该条件。
空结果页因此从「自己去猜哪条冲突」变成「一键退一步」。

### 2.4 ★ 置信门：默认值从 .70 改成 .60，并把被挡掉的人数说出来

这是本次唯一推翻既有默认的地方，理由是全套实测：

| 置信门 | 上衣黑 | 黑+女 | 黑+女+眼镜 |
|---|---|---|---|
| ≥0.50 | 119 | 14 | 6 |
| **≥0.60（新默认）** | **112** | **9** | **3** |
| ≥0.70（原默认） | 103 | 5 | 2 |
| ≥0.80 | 96 | 5 | 2 |
| ≥0.90 | 84 | 4 | 1 |

未过任何置信门的「黑衣女」是 **21 人**（21 个实体里 118 男 / 21 女里就是这批）。
**原默认 0.70 只能查到 5 个，漏 76%。** 原因是 softmax 未校准，每个条件都是一道独立的门，
3 个条件叠起来召回是乘性的。属性标注线早就定过「未校准 → conf ≥ .6」，0.70 是实现时随手写的。

但把默认改到 .60 只是缓解，**根本问题是「静默丢弃」**。所以新增 `conf_excluded`：
取值相符、档位也能判、只是置信度没过门的实体单独计数，在统计行明说
「另有 12 个取值相符但置信度没过门（拖低滑块可看到）」。9 + 12 = 21，账目完整。
**「查不到」和「没有」必须能分开**——这比调默认值重要。

## 三、接口变更

```
GET /api/attr/index
  conds        JSON 数组，AND 语义；与 field/value/min_conf 二选一（优先）
  min_conf     单条件置信下限，默认 .60（原 .70；见 2.4）
  cap          judge（默认，排除 n/a）/ ok（只留 ok，开了「只留可承诺字段」）/ off
  facet_mode   cross（默认）/ base（旧口径）
新增返回
  conds / cap / facet_mode   回显，便于排查
  cap_excluded               因档位能力不足被排除的实体数
  cap_excluded_by_field      {"戴眼镜": 3} 逐字段
  conf_excluded              取值相符、档位可判、仅置信度没过门的实体数
  drop_one                   [{f,v,n}] 仅当结果为 0 时给
```

前端 `AttrIndex.vue`：单字段下拉 → 条件构建器（字段 / 取值 / 置信度 / 删除），
卡片命中条件的标签描边，新增「不可判（X 档）」行，能力表里的空值从留白改成明写「不可判」。

## 五、结果导出：CSV 与截图包

检索的价值一半在「把找到的人交出去」。原来页面只能看，而且**只显示前 60 条**——
用户看到的和能带走的不是一回事。

| 入口 | 内容 | 用途 |
|---|---|---|
| 导出 CSV | 全部命中实体，一条一行，34 列 | 进 Excel / 交给人去现场找人 |
| 导出截图包 | zip = `entities.csv` + `crops/`（每条一张代表帧）+ `query.json` + `README.txt` | 脱离系统也能核对 |

### 5.1 导出走同一套筛选，不复制逻辑

`GET /api/attr/index/export?conds=...&fmt=csv|zip`，内部直接调 `attr_index()` 翻页取全量
（每页 300，最多 20 页）。**不另写一套过滤**：两个入口各写一遍，迟早给出不同的名单。
前端同理，同一个 `qparams()` 同时喂「查询」和「导出」，所以「看到的 112 条」和「导出的 112 条」
是同一次计算的结果，唯一差额是分页——这条差额在导出条上直说
（「页面只列了 60 条，导出含其余 52 条」），不做静默截断。

### 5.2 三个列设计决定

1. **每个字段拆成「取值 + 置信度」两列**（9 字段 → 18 列）。只给取值等于把置信度藏起来，
   下游没法按自己的标准再筛一遍。
2. **不可判写「不可判（S 档）」，置信度留空**——空表示「没有证据」，0 表示「证据指向反面」，
   这两种情况必须能分开。另有「不可判字段」一列，把该实体所有不可判字段并列出来。
3. **给帧号，不给跨机位时钟**：`机位 + 视频文件 + 起始帧/结束帧 + 起始时刻(mm:ss)` 足够回原片定位。
   段内秒只写成「段内相对时间」并写进 README，**不用它做跨机位加减**（OSD 才是唯一可信时钟）。

## 六、点开卡片：时间段 · 时间线帧 · 原片

一张代表帧判不了人。同一个人坐姿 / 走动 / 远近，**框高跨度中位 3.76 倍**——代表帧恰好落在
最不像的那一帧时，看的人会直接判「不是他」。卡片的「帧 N」原来只是个数字，现在点得开。

点开得到四样东西（`GET /api/attr/entity?entity=305-E012&n=5&w=520`）：

| | 内容 | 为什么必须给 |
|---|---|---|
| 时间段 | `01:25.4–02:32.8（67.4s）`、轨迹号、框高档位与框高 | 「这条轨有多长、在哪个机位」是判断可信度的前提 |
| 环境帧 | 16:9 场景窗口，**目标画黄框** | 画面里往往站着别人，不标框只能靠猜；也回答「他当时在哪」 |
| 时间线帧 | 实体时间段均分 5 帧，每帧带帧号 + mm:ss | 多姿态一次看完，不用在播放器里拖 |
| 原片 | `‹video›` 从 `/media/{cam}.mp4#t={t0}` 起播 | 想自己核对时不用另外找文件 |

### 6.1 三个必须做对的地方

1. **帧要吸附到该实体某一轨的观测点**。实体跨多个碎片轨，按 `[f0,f1]` 硬取中点很可能落在
   两段之间的空档里，裁出来是别人的半张脸。实测 `323-E100` 的 5 帧跨了 152 / 168 两条轨。
2. **必须从 1440p 原生裁**。`data/media/` 是 960×540 代理，200px 的人裁出来只剩色块
   （画面上的人被压到 75px 再放大）。原生 1.9 GB / 6 路在 `media-resource/multi-cemra/long-35min/`
   （`render.NATIVE_ROOT`），单帧 0.2–0.4 s，比代理只慢 0.1 s。
3. **并发打开同一个 1440p h264 会失败**。页面一次要 5 帧 → 5 个并发请求 → OpenCV 偶发
   `decode_slice_header error` → 读帧失败 → **404**（实测 5 张挂 2 张，重试同一 URL 又好了）。
   按 `(机位, 源)` 加锁串行 + 失败退 5 帧重试，10 路并发压测 10/10 通过。

### 6.2 一个被实测推翻的做法

最初用「框的倍数外扩」（pad=2.0）取环境。在细长的人形框上会退化成一根竖条：
849px 高的人 → 960×1382 的竖图，既不像环境也没法看（桌面上被 `object-fit:contain`
的留白吃掉大半屏）。改成**固定 16:9 场景窗口**（高 = max(人高×1.35, 600)，
撞边界按宽度反算）后，走廊与工位两种机位都稳定得到 960×540。

## 七、部署与两个环境坑

```bash
# 后端（读 webapp/backend/data/attr_index.json）
cd webapp/backend && python -m uvicorn main:app --host 127.0.0.1 --port 8010

# 前端（★ 必须 build 到 dist_attr 再只拷 index.html + assets，否则清掉 dist/faces）
cd webapp/frontend && node node_modules/vite/bin/vite.js build --outDir dist_attr --emptyOutDir false
cp dist_attr/index.html dist/ && cp dist_attr/assets/* dist/assets/
```

1. **`npx` 会因 C 盘满而 ENOSPC**（npm 要写 `AppData\Local\npm-cache`）。
   直接 `node node_modules/vite/bin/vite.js build` 可绕开 npm 缓存层。
   `npx vite build` 报 `ENOSPC` 时不是代码问题。
2. 同理，playwright 启动时浏览器 profile 默认落在 `%TEMP%`（C 盘），
   把 `TMP`/`TEMP` 指到 D 盘即可正常截图。
3. `dist/` 里的静态文件不需要重启后端；但 `main.py` 改了必须重启（本轮新增
   `/api/attr/index/export` 与 `/api/attr/entity`，只依赖标准库 `csv`/`zipfile`，无新依赖）。
   `render.py` 本轮也改了（`NATIVE_ROOT`、`crop_thumb(scene=, mark=, root=)`），同样要重启。
4. **后端冷启动后第一次打开页面要 70 秒左右**（`/api/tracks/*` 第一次要把 6 路轨迹读进内存建索引），
   之后每页 2 秒内。无头浏览器验证时 `waitForSelector` 要给到 120 s，不然会误判成「页面卡死」。
5. 前台起后端要用**工具的后台任务**（`run_in_background`），Git Bash 里 `nohup … &` 会在
   该次命令结束时被一起收掉 —— 本次踩过：探活 200，15 秒后端口已关。
6. ★★★ **后台任务只在本回合内有效**：回合结束任务被收，uvicorn 随之消失（日志停在
   `GET /api/health 200`，**没有 traceback、没有 shutdown**——这是被杀，不是崩溃）。
   要跨回合常驻只能由用户/另一个会话持有，或手动起。
7. ★★★ **多个会话同时改这份代码会互相杀端口**：谁重启都会 `taskkill` 掉端口占用进程。
   本轮就出现过「探活 200 → 一分钟后再探 404」的反复横跳。
   **判断顺序**：先 `netstat :8010` + `curl /api/health`，再怀疑代码；
   日志里没有 traceback 就别往 native crash 上想。

## 八、仍然成立的边界（不要因为界面好用了就忘）

- **6 个字段可交付**（性别 .993 / 上衣色 .908 / 上衣型 .993 / 下装色 .899 / 眼镜 .989 / 帽 .986），
  **2 个封顶**（背包 AP .458 / 拎东西 .656），页面标「参考」；
- **稀有字段的可用正例只有十几到二十几个实体**（帽 16 / 背包 22 / 拎东西 26），
  组合筛选能让它们被找到，但不能让它们变准；
- **下装只有「过膝 / 未过膝」**，不分裙与短裤（单帧无证据，已实测）；
- **索引的 673 是「像人」门后的数**，529 个实体被 `is_person` 挡掉，其中 323 机位 65% 不是人
  —— 这是检测层的问题，不是索引的缺陷，换素材才会变。

## 十、命名查询：存「怎么问」，不存「问到了谁」（19:50）

### 结论先行

条件组合可以存成命名查询、一键复原，但**只存条件（含机位/档位/闸门），不存名单**。
名单每次重算——索引会随新素材、重训、补标而重建，存下来的名单会安静地过期，
而没有任何东西会提示它过期了。这是这一层唯一的设计决定，其余都是它的推论。

### 接口

```
GET    /api/attr/queries              按 n_used 降序（常用的排前面）
POST   /api/attr/queries              {id?, name, conds, cam, band, cap}
                                      有 id 按 id 更新；无 id 按名字去重（同名 = 覆盖）
POST   /api/attr/queries/{id}/used    记一次使用（失败不影响检索）
DELETE /api/attr/queries/{id}
落盘   data/attr_queries.json（items[].conds/cam/band/cap/n_used/last_used）
```

★ 字段白名单取**索引实际有的 9 个字段**，不是标注 schema：`age_group` / `mask` 已不在索引里，
按标注 schema 校验会让「存下来的条件恒为空」，而且不报错。

### 两个只有真点才会发现的坑

1. ★★★ **id 用秒级时间戳会撞**：同一秒连存两条 → 两个选项 `value` 相同 →
   选谁都套用第一条（实测两条查询都变成 `id=q1112193553`，页面无任何异常提示）。
   改毫秒时间戳 + 碰撞自增。
2. ★★ **Playwright 的 `APIRequestContext` 会走本机代理**：本机 `HTTP_PROXY=127.0.0.1:4282`，
   用它打 `127.0.0.1:8010` 会**挂住直到超时**（页面内 `fetch` 不受影响）。
   造数据要用页面内 fetch 或 `curl --noproxy '*'`。
3. ★ 顺带确认：`curl` 也不要用默认设置——代理在时会把「连接被拒」变成 **502**，
   容易误判成「服务在跑但报错」。

### 验证（真点 + 断言）

| 操作 | 结果 |
|---|---|
| 搭「上衣黑 + 戴眼镜」→ 存为「黑衣戴眼镜」 | 保存反馈「已存」，下拉出现「黑衣戴眼镜 · 2 条」 |
| 刷新页面 | 查询仍在（已落盘），下拉复原一致 |
| 套用 | 条件复原为 `top_color=黑` / `glasses=是`；命中 **98**，另有 3 因档位不可判、19 置信不足（98+19=117） |
| 删除 | 下拉回到「（未选择）」，文件条目 0 |
| 手机 414 px | 横向溢出 0 |
| 接口断言 `tmp/attr/test_queries_api.py` | **13/13**：同名覆盖不新增、按 id 改名、conf 夹到 [0.5,.99]、非法字段 400、空条件 400、空名字 400、同字段两条去重、n_used 排序、删除 |
| 控制台 | 0 error |

★ **示例名字要按数据挑**：「黑衣戴帽」在这批素材里**恒为 0**（帽=是 16 人、全是白上衣），
写进文档当例子会让人以为功能坏了。留库的两条种子是「黑衣戴眼镜」（98）与「背包或拎包的人」（13）。

### 边界

- 存在后端 `data/` 下，**同机共用**，不做账号隔离、不跨设备同步；
- 名字 ≤24 字，同名覆盖（刻意如此：改条件后仍叫这个名字时不该多出一条）；
- 与查询/导出**共用同一份 `conds`**，所以「套用后看到的」和「导出的」还是同一批人
  （导出条里的 `query.json` 就是命名查询的数据形态）。

## 十二、图片试跑：上传一张图，走真实容器（23:10）

前面十节都只能查**已入库的 673 个实体**。要给外部图片算属性，要么另写一套推理，要么直接用
打包好的服务——选后者：控制台加一个页签，把图转发给远程 `hc-attr:1.3`，不重复造推理。

```
浏览器 ──上传──> 本地后端 /api/attr/infer ──转发──> 192.168.11.16:18080 /v1/analyze
                     （体积/超时/报错在这一层把关）              （GPU、模型、档位闸门都在这）
```

**为什么不在浏览器直连**：算法服务没开 CORS，跨源读 JSON 会被拦；浏览器所在网段也不一定通算力机；
上传上限和超时只该有一处决定权。

### 交互与五个决定

| 决定 | 理由 |
|---|---|
| 原图上叠编号框 + 右侧卡片，点框/点卡片互相同步 | 只给一堆数字对不上人；框能立刻回答「这是谁」 |
| 默认 `crops=1`，每人带一张裁图 | 能看见模型实际输入的是什么，避免「框对了但图喂错了」这类误判 |
| 「整图当一个人」开关（`boxes=full`） | 已裁好的单人图，YOLO 检不出来（实测 PA 58×148 裁图检出 0 人）；开了之后 9 字段齐全 |
| 档位 + 不可判显式展示 | S/M 档直接写「不可判」而不是给个值；与索引页的能力矩阵同一套 `capability` |
| 端到端与服务内计时分开报 | 端到端含上传与代理；服务内是 det/emb/head。混在一起会把 PNG 上传算成模型慢 |

### 两个真 bug（都是点了才发现）

1. **结果页把 `<input type=file>` 一起收起来了**。为了不重复显示同一张图，结果出来后隐藏上传区，
   而 input 原本在它里面 —— 于是「换一张」点了没反应，只能先清空。修法：input 提到根节点，
   按钮区保留「换一张 / 清空」。
2. **`requests` 默认读系统代理**。本机开着代理时，`http://192.168.11.16:18080` 会被拦，
   返回代理的 `502 upstream connect failed`，看着像算法服务崩了。修法：`Session.trust_env = False`
   ——局域网调用不走代理。这条对任何「内网 HTTP」脚本都成立。

|---|---|
| 318 整帧（1920×1080，4 人） | 4 框 / 4 卡；#0 蓝长袖·黑长裤·眼镜是；端到端 335 ms（服务内 320 ms） |
| 已裁单人图（58×148，`boxes=full`） | 1 卡，帽=**是 100%**；`is_person` 只有 .24（域外偏低，文案已说明只作提示） |

- 这是**单张试跑**，不是批量入库：结果不写回 `attr_index.json`，也不会产生实体编号。
- 外部图片属**域外**，精度按验收文档打折（眼镜 .838 / 帽 TPR .52 / 背包 TPR .25）；

## 十四、HSV 显式颜色特征（2026-11-13，证伪）

§十三 的结论指向「EG2 对色相不敏感，颜色该用像素直方图」。做了，**证伪了**。

### 做法

`tmp/algo/hsv_feat.py`：按框内相对高度取两条带（躯干 0.12–0.48、腿 0.52–0.95），
横向只取 15%–85%（避开背景），每带算 H 直方图 12 bin（**按 S 加权**，否则黑衣的色相是纯噪声）
+ S 直方图 4 bin + V 直方图 4 bin + 颜色矩 5 项 = 25 维，两带共 50 维。

### 结果（域内 457，身份留出 CV，k 按最少类取）

| 字段 | EG2 768 维 | HSV 50 维 | 拼接 |
|---|---|---|---|
| top_color（8 类，n=439） | **.8884** | .5809 | .8793 |
| bottom_color（5 类，n=294） | **.9014** | .6599 | .8946 |

HSV 单独用差 30 个点；拼进去反而**比纯 EG2 低 1–2 个点**（768 维降到 64 维给 HSV 让位的损失，大于 HSV 带来的增益）。

### 为什么失败（两条，都记下来）

1. **EG2 已经隐含编码了颜色**。它是在图文对上训练的，自然语言描述里大量出现"穿黑衣服的人"，
   颜色信息已经进嵌入。50 维直方图的信息量比 768 维语义嵌入低一个量级。
2. **会议室场景大量坐姿，腿带取到的不是裤子**。自检里 `bottom_color` 按真值分组，
   「白」的 V 均值 0.154 反而低于「黑」的 0.209 —— 说明腿带取到的是椅子/桌子/地板。
   这也解释了域内 `bottom_color` 为什么 41% 是空标注：**下装在这个视角下本身就经常不可见**。

### 副产物：一个对产品的判断

`bottom_color` 的瓶颈不是模型而是**可见性**。域内 457 条里 186 条（41%）下装无法判定，
剩下能判的又多是坐姿。继续在颜色上堆特征/数据的边际收益很低，
真要提高只有两条路：**改采集视角（俯角再大一点，能看到腿）** 或 **把「不可判」当成一等公民**
（置信度低于阈值就不输出，而不是硬给一个"最近色"）。

→ 所以 §十三 里"用 HSV 救颜色"这条建议撤回。下一步只剩标注扩量这一条实质路径。

## 十五、开词表：只给结构不给选项，让 VLM 自己答（2026-11-13）

§十三/§十四 的结论是「闭集头涨不动」。换个问法：**不给候选值，只告诉它每个键是什么意思，
让模型自己写**，会不会更准、更像人？

### 设置

- 模型 **Qwen3-VL-4B-Instruct**（ModelScope 下的 safetensors，bf16，18 GB 显存，约 4.9 s/张）
- 输入：按 `attr_items.json` 的 bbox 从**原生 1440p** 回裁，pad 12%，短边不足 384 才放大
- 样本：251 条 item（234 实体），筛「已标注 ∧ 非 skip ∧ 人 ∧ h/w≥2.0 ∧ 非 S 档」
- prompt 只写**键名 + 该键问什么**，一个候选值都没列；额外加 `summary` 键要「一两句话描述整体外观」

### 核心结果（251 条，zero-shot）

| bottom_type | 237 | 2 | 12 | .964 | .948 |

| backpack | 49 | 0 | **201** | .959 | .197 |

「同口径 acc」= 在它给出可折回答案的子集上；「总 acc」= 分母是全部 GT 有值的项。

### 发现的第一个问题：它不是看不清，是太保守

先按框高分桶看「不可判」率，**和分辨率几乎无关**：

| 字段 | h<300 | 300–600 | h≥600 |
|---|---|---|---|
| glasses | 86/103 (83%) | 36/55 (65%) | 51/93 (**55%**) |
| hat | 78/103 | 40/55 | 68/93 (**73%**) |
| backpack | 88/103 | 42/55 | 71/93 (**76%**) |

h≥600 的样本人已经占满画面，背包仍有 76% 判「不可判」。根因是 v1 prompt 里那句
「看不出来的项写不可判，不要猜」被过度执行。

### 第二个问题：`carrying` 的定义和 GT 不一致（不是模型错）

模型答「手机」23 次，GT **全是「否」**；答「文件夹 / 雨伞 / 白色袋子」，GT **全是「是」**。
说明 GT 口径是「拎大件」，手机不算。修正归一化规则后 `carrying` 从 **.241 → .648**。

> 这条要记住：**任何"模型不准"的结论，先核对字段定义再下判断。**

### A/B：把「不可判」的触发条件收紧

v2 prompt 只改一句：*「只要这个部位出现在画面里，就按你看到的情况直接回答；没有看到就是没有。
只有该部位完全不在画面内才写不可判」*。**依旧不给任何候选值**，只改作答策略。

同批 100 张：

|---|---|---|---|---|---|---|
| gender | .94 | .979 | 1.00 | .960 | +.06 | −.019 |
| top_color | .97 | .784 | .97 | .794 | .00 | +.010 |
| top_type | .95 | .946 | .94 | .946 | −.01 | −.001 |

| bottom_type | .99 | .956 | .98 | .966 | −.01 | +.011 |

- **`glasses` / `backpack` 拿 15–17 点准确率换覆盖率** —— 因为 v1 只在"看得很准"的样本上开口，
  v2 被要求对每张都给答案，就把漏检（GT 是"是"但画面里没看出来）暴露出来了。
- 这是一条干净的 **覆盖–精度权衡曲线**：v1 = 高精度低召回，v2 = 高召回低精度。

### 与闭集头同批对比（100 张，同一批 GT）

|---|---|---|---|

| bottom_color | .924 | .893 | −3.1 |
| bottom_type | .967 | .966 | −0.1 |
| glasses | .908 | .827 | −8.1 |
| hat | 1.000 | .904 | −9.6 |
| backpack | 1.000 | .750 | **−25.0** |
| carrying | .912 | .732 | **−18.0** |

**闭集头是训练集内预测（这 251 条全在 457 条标注里），VLM 是 zero-shot。**
即使这样闭集头仍全面更强，只有 `top_type` 被反超。所以：

> **在「固定字段的准确率」这件事上，专门训练的小模型仍然赢，4B 的通用 VLM 不够。**

### 但 VLM 给了两样闭集头给不了的东西

**1）词表外的表达能力。** 它在 `top_color` 说了「米色」18 次、`bottom_type` 说了「长靴」、
`carrying` 说了「拖把」「白色物品」。闭集头永远说不出来 —— 词表是死的。

**2）`summary` 的整体描述。** 抽样 16 条（GT 附后）：

```
戴眼镜男子按电梯            女保洁员手持拖把           低头看电脑
黑衣男戴眼镜持杯            穿蓝T恤灰裤男子            穿红夹克黑裤
戴帽穿卫衣的女生            穿棕色夹克男子             穿黄夹克低头看手机
```

它补的是**动作、职业、交互对象**（按电梯、手持拖把、低头看电脑）—— 这 9 个字段里根本没有。
而且描述里含的信息量比 9 个字段加起来还多，可以直接拿去做检索的关键词来源。

### 判断

- **不要**用 4B VLM 替掉闭集头做字段判定：`backpack` −25、`carrying` −18、`top_color` −12.6，
  差距不是调 prompt 能补的。
- **要**用它的 `summary`：这是新能力，成本 5 s/图，可离线批量跑。
- **最有价值的用法是标注入力**：拿 VLM 给剩下 1005 个未标注实体出**预填候选**，
  人工只做校对而不是从零标 —— 正好解决 §十三 里「标注扩量 2000 条」的瓶颈。
  v2 的覆盖率 96% 说明它基本每项都敢开口，校对比空标快得多。

### 本轮踩的坑（都记下来）

1. **远程机器完全断外网**（连 pypi 都 000），模型只能本机下好再送过去。
2. **SSH 的 sftp/exec 传 GB 级文件，写入完成后新会话读不到**（`stat` 当时能读到 4.63 GB，
   事后 `os.stat` ENOENT，磁盘占用却少了 8 GB）。32 MB 以下正常。
3. **走 HTTP 才对**：本机 `python -m http.server` + 远程 `curl --noproxy '*'`，
   实测 **92.8 MB/s**（SSH 只有 29 MB/s），8.3 GB 两分钟下完。
4. **本机起的 http.server 在命令结束时被回收** → 必须用工具的后台模式常驻，
   否则远程 curl 会一直挂着、文件一个都不落盘（表现为"目录空但进程在跑"）。
5. `pkill -f <pattern>` 会把执行它的 bash 自己匹配上（命令行里含 pattern），
   结果是 SSH 会话自杀、退出码 -1。用 `pkill -x curl`。
6. **`carrying` 的 .241 是定义差异不是模型差** —— 归一化里剥离「手机」后回到 .648。

## 十六、VLM 预填标注页 + summary 入库（2026-11-13）

§十五 的结论是「VLM 不宜替字段判定，但适合标注入力与整体描述」。本轮把这两条落地。

### 一、预填标注页（118 个未标注实体）

| 环节 | 结果 |
|---|---|
| 未标注实体 | **640**（1028 − 389 已标注） |
| 其中 `is_person≥0.5` | **294**（另 346 是疑似假框） |
| 有 bbox（`attr_items.json` 有记录） | 41 |
| 无 bbox（需检测器重定位） | 253 |
| 检测器能检出人 | **82 / 167**（S 档 86 个已跳过）→ **失败率 51%** |
| 最终裁出可标图 | **118**（bbox 精确 36 + 重定位 82） |

`attr_label_vlm.html`：118 张卡片、1.4 MB 单文件、手机可开。
**预填非空项 850 / 1062（80%）**，其余留空让人工选。

三个设计决定：

1. **折不回词表的一律留空，不硬填最近的词。** 模型说「米色」「长靴」「上衣」，硬映射成"棕""长裤""长袖"
   等于给它编答案；留空 + 底部显示**模型原话**，标注者一眼能看出该不该改。
2. **颜色兜底匹配标注页词表。** 域内归一化只有 8 色（不含黄/橙/粉），但标注页词表有 11 色。
   模型说「黄」时若按 8 色判成"词表外"就会留空，标注者会以为模型没说 —— 加一层直接用原话里的词。
3. **卡片顶部显示 `summary`**（"穿黄衣低头看屏幕"），比 9 个 chip 加起来的语义还多。

### 二、summary 入库与检索

- `patch_summary.py` 把 summary 注入索引 → `attr_index_v10.json`，**覆盖 351 / 1028 实体**
  （118 来自未标注批，233 来自 §十五 评测批按 entity 归并）。
- 后端 `/api/attr/index` 返回 `summary` 字段；`q` 搜索参数**也搜 summary**（原来只搜实体号）。
- 前端卡片加 `.sumline`（左侧色条 + 强调色）。

效果（真实查询）：

| 查询 | 命中 | 说明 |
|---|---|---|
| 拖把 | **4** | 305-E011「女保洁员手持拖把」、316-E028「灰衣黑裤持拖把」、323-E066「女保洁员持拖把」 |
| 按电梯 | **1** | 343-E035「戴眼镜男子按电梯」 |
| 低头看电脑 | **2** | 305-E012、305-E105 |
| 手机 | **21** | —— |

**「拖把」「电梯」这些概念在 9 个字段里根本不存在**，闭集头永远检索不到。这是 summary 唯一但足够的价值。

反例（同一个实体，两条信息互补）：

```
305-E011
  9 字段：女 / 灰上衣 / 短袖 / 黑长裤 / 眼镜是 / carrying=否
  summary：女保洁员手持拖把
```

`carrying` 判"否"是按「拎大件」的口径（§十五），但她确实手持拖把 —— 检索的时候，
"手持拖把"这个信息只能从 summary 拿。

### 三、这轮暴露的结构性问题：裁图元数据缺失

640 个未标注实体里：

- **346 个 `is_person<0.5`** —— 索引里本来就有大量疑似假框（与「假框率 316 39.8% / 323 47.9%」一致）
- 294 个真人里**只有 41 个有 bbox 记录**，其余 253 个只能靠检测器在场景图上重新找，
  而重定位**一半失败**（场景图里人太小，rfdetr 检不到）

→ 想扩标注，卡点不在"没人标"，而在**没有坐标**。要系统性地扩到 2000 条，
得先把 `attr_items.json` 的 bbox 覆盖从「仅已标注」扩到全量 —— 这是件一次性的事，
比反复用检测器兜底划算得多。

### 四、下一步（按性价比）

1. **把 bbox 补齐到全量**（用现有的 tracks 数据，不重新检测）→ 之后所有未标注实体都能精确裁
2. 补完后再跑一轮 VLM 预填，可标池从 118 → 约 250
3. summary 只覆盖 351/1028，剩余 677 个需要再跑约 60 分钟；建议等 bbox 补齐后一起跑（一次裁图两用）

## 十七、补齐 bbox：可标池 118 → 166（2026-11-13）

§十六 的卡点写的是「扩标注的真正瓶颈不是没人标，是没有坐标」。这轮把它解决了。

### 关键发现：坐标一直都在，只是没接上

`webapp/backend/data/tracks/{cam}.json` 里每条轨都有**全部帧**的 bbox，
`entities.json` 又记着每个实体由哪些轨组成 —— 两下一拼，每个实体的代表帧 bbox 就出来了，
**根本不需要检测器**。上一轮用 rfdetr 在 `ent_crops` 场景图上重定位（51% 失败），纯属绕远路。

`tmp/algo/build_ul_plan.py`（代表帧口径与 `build_items.py` 完全一致，保证新老样本可比）：
框高 ≥0.9×轨内最大值 的帧中取最接近轨迹中点的那帧；门槛 框高 ≥45 px、框宽中位 ≥22 px、宽高比 0.15–1.05。
