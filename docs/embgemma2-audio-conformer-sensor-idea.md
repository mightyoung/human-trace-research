# EmbeddingGemma 2 的音频塔（Conformer）能不能吃设备传感器信号？

> 日期：2026-10-18 ｜ 对象：本地 `models/google--embeddinggemma-2`（744M，Apache-2.0）
> 方法：结构解剖（config.json / 模型卡）+ 三条路线的最小实测（合成信号）+ 近邻文献
> 证据分级：【结构】= 读配置与权重键；【实测】= 本机 CPU 跑出的数；【文献】= 外部工作；【推断】= 推导

---

## 0. 结论（先行）

**1）它的音频部分确实是 Conformer，而且是为流式设计的窄版。**
`gemma4_audio`：12 层、hidden 1024、8 头、depthwise 卷积核 5、**分块局部注意力**
（chunk=12 帧、左看 13 帧、右看 0 帧）、4× 下采样 → **40 ms/token（25 token/s）**，
16 kHz / 128 mel / 10 ms hop / log(mag+1e-3)。单条上限 280 token ≈ **11.2 s**，
更长的音频要切窗后平均。【结构 config.json、README】

**2）能不能用传感器信号？分三种情况，实测结论不一样：**

| 信号类型 | 路线 | 实测（合成数据） | 判断 |
|---|---|---|---|
| 高频振动（≥kHz，冲击/谐波） | 直接当 16 kHz 波形喂音频塔 | 类间可分性 100%（4 类×5 例），但文本查询只中 2/4 | 🟡 特征可用，**语义不可用** |
| 多通道慢信号（温度/CO₂，1 Hz 级） | 同上（升采样到 16 kHz） | 升温 vs 平稳 cos **0.922**；阶跃 vs 平稳 **0.969** | ❌ 完全分不开，别做 |
| 多通道慢信号 | 画成图走视觉塔 | 可分性 100%，文本查询中 **3/4** | ✅ 目前最靠谱的一条 |

**3）一句话判断：** 想拿它做"用一句话查传感器历史"，只有**图表路线**勉强成立（3/4，且是 4 类合成数据）；
想拿它做**振动异常检测**，可以做，但价值来自"特征提取器 + 自己的头"，不是它自带的语义空间。
**1 Hz 温度曲线走 Conformer 是纯粹的错误用法**——它会把所有慢信号映射到几乎同一个点。

**4）真正的机会不在"复用这个塔"，而在"复用这个共享向量空间"**：把传感器画成图 → 与摄像头画面、
文本查询放进同一个 768 维库，做跨模态检索与**无摄像头的人数代理**。这是与本项目最契合的方向（§4）。

## 1. 结构事实

| 项 | 值 | 含义 |
|---|---|---|
| 塔类型 | `gemma4_audio`（USM 系 Conformer） | 卷积 + 自注意力的混合编码器 |
| 层数 / 宽度 | 12 层 / hidden 1024 / 8 头 | 比 ASR 常用的大 Conformer（17 层×512）更深更宽 |
| 卷积 | depthwise 1-D，kernel 5 | 抓局部瞬态（冲击、起振） |
| 注意力 | chunk 12、left context 13、right 0、logit cap 50 | **流式**：每帧只看当前块 + 13 帧历史，不看未来 |
| 下采样 | 两层 stride-2 卷积（128→32 通道） | 10 ms 帧 → **40 ms/token** |
| 输入 | 16 kHz 单声道，128 mel，窗 20 ms，hop 10 ms | 与 Whisper/USM 一致的声学前端 |
| 输出 | 1536 → `embed_audio` 512 → 文本塔 768 | 与文本/图像共享同一空间 |
| 预算 | 280 soft token/条 ≈ 11.2 s；整体 8192 token | 长音频需切窗 |
| 许可 | Apache-2.0 | 可商用（对比 StartLux 的 CC BY-NC） |

**关键点：它没有"时域多尺度"设计。** 40 ms/token 对语音合适，对 1 Hz 温度就是 40 个 token 看同一个数；
对 50 Hz 振动则是每 token 覆盖 2 个周期——刚好够看"有没有冲击"，不够看"转速的缓慢漂移"。
这两件事决定了 §1 表格里的对错。

### 与本项目现有部署的关系

`docs/embgemma-strip-feasibility.md` 已经证明：推理期把 `audio_tower`（304.8M）+ `vision_tower`（167.4M）
当死重剥离，向量**逐位不变**、显存省 1.845 GB。要用音频塔，等于把那 0.6 GB 加回来，
并且要单独跑一个进程（不走现有 FastEncoder 的 RADIO 桥接路径）。这是明确的成本项。

## 2. 三条路线的实测

**方法**：合成 4 类信号 × 5 例（8 s），L2 归一化后 1-NN 留一法分类；文本查询用非对称检索前缀
`task: search result | query: …`（模型卡推荐）。全部 CPU fp32。
脚本 `tools/embgemma2_sensor_probe.py`，产物 `output_crosscam/analysis/embgemma2_sensor/`。

### 2.1 路线 A：振动类信号直接进音频塔

| 指标 | 结果 | 解读 |
|---|---|---|
| 1-NN 留一分类 | **20/20 = 100%** | 四类（稳态电机 / 周期冲击 / 升速扫频 / 白噪）线性可分 |
| 文本→音频 top-1 | **2/4 = 50%**（随机 25%） | "稳态嗡嗡声"和"升速"都命中了噪声样本 |
| 单条耗时 | 0.86 s / 8 s 音频（CPU 预热后） | 约 9× 实时 |

**解读**：它确实把振动当"声音"在编码（冲击=瞬态，扫频=音高变化），类别结构在；
但**语义对齐很弱**——它听过的"机器"是真实录音，不是合成正弦。真实设备声可能好一些，但这需要真实数据才能判断。

### 2.2 路线 C：1 Hz 温度曲线进音频塔（负结果）

| 比较 | 余弦 |
|---|---|
| 升温 vs 平稳 | 0.922 |
| 阶跃 vs 平稳 | 0.969 |
| 升温 vs 阶跃 | 0.935 |

三条曲线在 768 维里几乎是同一个点。**结论：慢通道不要走音频塔**，任何"温度异常检索"都不可能成立。

### 2.3 路线 B：多通道时序画成图，走视觉塔

图：2 面板（温度、振动 RMS）× 240 分钟，matplotlib 512×384。

| 指标 | 结果 | 解读 |
|---|---|---|
| 1-NN 留一分类 | **20/20 = 100%** | 平稳/上升/阶跃/周期 四类可分 |
| 文本→图 top-1 | **3/4 = 75%** | 唯一失败："平稳" 命中了 "阶跃"（两者前半段都平） |
| 单图耗时 | 6.9 s（CPU，fp32） | 慢，但可离线批处理；GPU 上按项目既有 22 ms/图 量级 |

**解读**：视觉塔见过大量图表，语义对齐明显好于音频塔。这是"用一句话查历史时段"唯一可行的路线。
注意：现有生产编码器把 `vision_tower` 换成了 RADIO 桥接 + 自训 W（为人脸裁剪训练），
**图表会落在 W 的分布外**；走这条路要用原版视觉塔，不能直接复用 FastEncoder。

### 2.4 实测的边界（必须写清楚）

- 全部是**合成数据**，4 类、每类 5 例、单次运行；100% 只说明"结构可分"，**不代表真实场景精度**；
- 文本查询只有 4 条，75% 的置信区间极宽（约 30%–95%）；
- 真实传感器有漂移、缺失、量纲差异，合成数据完全没有覆盖；
- CPU 耗时不能外推到生产（项目在 L20 上测过 22 ms/图）。

## 3. 近邻研究

| 工作 | 做了什么 | 对我们的含义 |
|---|---|---|
| **VGGish → 轴承故障**（Di Maggio, Sensors 2023）【文献】 | 用音频预训练 CNN 的特征，微调后判别轴承内圈/外圈损伤 | **音频→振动迁移成立，但必须微调**；冻结特征直接线性探测效果有限 |
| **Conformer HAR**（Kim, Sensors 2022；Seenath, Sensors 2023）【文献】 | 把 Conformer 搬到 IMU 人体动作识别，WISDM 98.1%、USCHAD 96% | Conformer 的"卷积抓局部 + 注意力抓长程"确实适配传感器时序，**但都是从零训练的小模型**（3–10M 参数），不是 300M 预训练塔 |
| **TSPulse**（2025）【文献】 |  tiny 时序模型，零样本"register embedding"做相似检索，比 MOMENT/Chronos 高 25–100%，模型小 40× | **专用小模型 > 通用大模型**做时序检索；我们要的"按形状找片段"已有更便宜的解法 |
| **SensorLM**（Google, NeurIPS 2025）【文献】 | CLIP/CoCa 式传感器-语言预训练，59.7M 小时可穿戴数据 + 自动 caption 管线 | "文本查传感器"必须**专门对齐训练**；靠音频塔零样本只能碰运气 |
| **CLaSP**（Hitachi, EUSIPCO 2025）【文献】 | 对比学习对齐波形与描述，mAP@10 >0.5；caption 由"前向合成 + 后向特征描述"两路生成 | 若要做语义检索，**自动生成 caption 是可行工程路径**（"温度持续上升""出现周期性尖峰"） |
| **E-Nose + TSFM 评估**（2026）【文献】 | 冻结的 Chronos-2 / MOMENT 嵌入在气体传感器上表现差，微调+融合才可用 | **通用时序/音频嵌入零样本迁移到专用传感器，普遍不灵**——与我们的实测一致 |

**综合判断**：文献和实测指向同一结论——
**零样本语义对齐不可靠；可靠的是"专用小模型"或"微调后的特征"。**
EmbeddingGemma 2 的音频塔在这条光谱上属于"贵的通用特征提取器"，不是"开箱即用的传感器理解器"。

## 4. 我的 idea：把传感器做成"第二模态的人流/设备信号"

不要问"这个塔能不能吃传感器"，要问"**共享的 768 维空间能换来什么别人做不到的事**"。
答案是三件，按 ROI 排序：

### 4.1 设备健康（最快见效，2 周可出原型）

边缘盒子（NVR/工控机）本身就有风扇转速、硬盘振动、CPU 温度。
- **做法**：振动/风扇信号 → 音频塔（或直接用 §3 的 3M 参数小 Conformer）取特征 → 每台设备一个正常态基线 →
  马氏距离/重构误差报警。**不用文本、不用语义**，绕开实测里最弱的一环。
- **成果**：故障前 3–7 天预警（风扇积灰、硬盘轴承磨损），把"到现场才发现"变成"提前换件"。
- **验收**：真实故障事件 ≥ 20 例时，AUC ≥ 0.9，误报 ≤ 1 次/台/月。

### 4.2 无摄像头的人数代理（战略价值最高，但需要配对数据）

这是与本项目最契合的一条：隐私敏感区（走廊、更衣区、卫生间前室）不装摄像头，
用 CO₂ / 温湿度 / 门磁 / 振动（脚步）估计人数或"有人/无人"。
- **做法**：多通道时序 → 图表 → 视觉塔 → 768 维；用摄像头的计数结果做**弱监督标签**训练一个回归头
  （几十维就够，不必微调 170M）。
- **成果**：给现有产品加一条"无摄像头点位"的报价线，或给现有摄像头点位做交叉校验（两路信号打架 → 人工复核）。
- **验收**：MAE ≤ 1 人（办公室 0–10 人场景），或"有人/无人"F1 ≥ 0.9。
- **风险**：需要同一时空的传感器 + 摄像头配对数据；没有就先做 4.1。

### 4.3 历史时段语义检索（体验层，不是核心）

运维/安保用一句话找片段："上周三下午温度突然掉下去的那段"、"夜里振动一直不停的那段"。
- **做法**：图表路线 + 非对称检索前缀；索引进现有向量库，和摄像头画面共用一套检索。
- **成果**：复盘效率从"拖时间轴"变成"搜一下"。
- **验收**：50 条真实查询 top-3 ≥ 70%。
- **注意**：实测只有 3/4；真实查询会涉及"哪一天/哪个设备"这类元数据，**必须和结构化过滤结合**，别指望纯语义。

**推荐顺序：4.1 → 4.2 → 4.3。** 4.1 不依赖新数据、当天就能验证；4.2 是战略项但要等配对数据；
4.3 是锦上添花，且已有更便宜的替代（TSPulse 类小模型）。

## 6. 失败判据（提前写好，避免沉没成本）

任一条成立就停：
1. 真实振动数据上，音频塔特征 + 线性头的 AUC 不高于手工特征（RMS/峭度/FFT 前三阶）**+5pp**；
2. 图表检索在 50 条真实查询上 top-3 < 50%；
3. 传感器→人数回归 MAE > 2 人（10 人以内场景）；
4. 单台设备日均推理成本高于其年维护费的 1%。

---

## 7. 下一步需要什么

1. **一段真实振动**（哪怕手机贴着机柜录 10 分钟）+ 一次已知事件（开机/风扇全速/硬盘寻道）；
2. **一组配对数据**：任一房间的 CO₂/温度 + 摄像头人数，同时间段 ≥ 3 天；
3. 决定要不要为 4.2 引入 CO₂ 传感器（几十元，比再上一个摄像头便宜一个量级）。

有第 1 项就能当天验证 4.1；有第 2 项就能两周内验证 4.2。
