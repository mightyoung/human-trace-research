## 2. 分组与做法

### A 组 · 血缘闭环（G1 G2 G3）

这三项一起做才有意义：stale 判定依赖「输入指纹」，而指纹来自 dataset 与 model。

#### A1 · `stale` 判定

**为什么**：SCRFD 三文件修复后，所有历史人脸坐标产物都不能与新的混用，但台账里它们仍标 `succeeded`。这类「输入变了、结果没重跑」的状态，现在只能靠人记。

**做法**

1. 给 `run` 补一列 `input_hash`（或写入 `env_json.inputs`）：`sha1(dataset.snapshot_hash + model.weights_sha1 + code.sha1 + 关键 params)`。
2. `tools/ops_stale.py`：
   - `check [--dry-run]`：遍历 `succeeded` 且 `kind in (infer, encode, eval, train)` 的 run，重算当前输入指纹，与记录值比对；
   - 不一致 → `status='stale'`，并在 `note` 写清「哪个输入变了」（数据 hash / 模型 sha / 代码 sha / 参数）。
3. 只在**显式调用**时判定，不在启动时自动跑——避免一开服务就把 41 条全标黄。

**验收**：人为改一条 run 的 `input_hash`，`check` 能把它标 `stale` 且 `note` 指出差异字段；未改的保持 `succeeded`。

**风险**：历史 41 条 run 都没有 `input_hash`，首次判定要么补算、要么跳过。建议**跳过并标注 `input_hash=NULL`**，不追溯猜测。

#### A2 · 数据集登记

**为什么**：`dataset` 只有 3 条，且 2 条无 hash。训练时 `--dataset ds_e21_slice_v1` 会创建一条空壳记录，等于没登记。

**做法**

- 写 `tools/ops_dataset.py`：
  - `scan --root <dir> --kind video_set --dialect clean2`：扫目录，算文件数、总字节、`manifest` 的 sha1（文件列表 + size + mtime 排序后哈希），写 `dataset`；
  - `ls` / `show <id>`。
- 先补登 3 份真数据：`6cam_synced10`（已有 hash）、`1012`（29h）、`e21` 切片（leader 正在产出）。

**验收**：`ops_run --dataset` 引用时，dataset 记录已有 `snapshot_hash` 而非空值；重复 scan 幂等（hash 不变则不新增）。

#### A3 · 模型注册

**为什么**：`model` 表 0 条。8 个现成权重没有身份，训练产出的 `best.pt` 也没有身份。指标溯源断在这一环。

**做法**

- `tools/ops_model.py`：
  - `register --path models/face/scrfd_2.5g_bnkps.onnx --name scrfd_2.5g --backbone SCRFD --license ...`：算 sha1、bytes，写 `model`（`version` 用 sha1 前 8 位）；
  - `from-run <run_id>`：把训练 run 的 `best.pt` artifact 提升为 model，`trained_by_run=run_id`；
  - `ls` / `show`。
- 先注册 8 个现成文件（5 face onnx + 3 reid pth），再补 35 个训练 run 产物中的可用模型（先只登记 `global_*` 与 `base_*` 这类有代表性的，不批量灌 35 条）。

**验收**：`#/runs` 详情里「模型」字段能点到一个 `model` 记录，且有 `weights_sha1`；`model` 页面（若做）能列出 8 条。

> A 组做完，才能回答设计文档 P2 的验收标准：**任取一个历史数字，能点到 run → 数据 → 模型 sha**。

### B 组 · 标注统一（G4 G8）——工作量最大

#### B1 · 标注页接管 `annotation_item`

**为什么**：这是**唯一还在双轨运行**的部分。三个页面 1581 行代码，各自把判定写进 4 个不同结构的 json，台账靠 `_ops_mirror` 反向同步。已经因此出过两次同类事故：

- 镜像缺 S6-b 前缀路由 → 12 条判定分属两个任务（§14.1）
- 统计口径按文件算 → 同一批数据得出相反结论（§11.2）

**做法（分三步，每步可独立上线）**

1. **读切换**：新增 `/api/ops/queue?task_id=` 返回 item 列表（`payload_json` 内含候选图 URL/缩略图定位），前端三页改为读它；**写入仍走老接口**。
   - 这一步不改写入，风险最低，但已能让「待判数」有唯一来源。
   - ✅ **2026-11-09 完成**。前置修了证据缺口（`label.data_json` + 回填 630 条），
     三页数字与台账一致（241/107/75/75/45/28）。详见设计文档 §19。
2. **写切换**：三页改为 `POST /api/ops/label`（已存在），`_ops_mirror` 反过来由台账**投影**到 json（`project_item` 已有）。
   - 保留双写，json 由台账单向生成，不再接受直接写。
3. **下线老接口**：`/api/labels`、`/api/faces/label`、`/api/truth/labels` 标记 deprecated，观察一周无调用后移除。

**验收**：三页各判 5 条，`verify` 零差异；关掉 json 写入后页面仍正常；老接口调用计数为 0。

**风险**：`AnnotateView` 552 行里混着候选对、倒影、掩膜三种交互，切读容易、切写要逐个改 `saveLabels` 调用点（该页 3 处，三页合计 6 处）。建议按 ①→②→③ 分批，不要一次重写。

#### G8 · 导出与 run 绑定

**为什么**：标注结果要给训练用，现在靠手工拷 json，无法证明「这份数据用的是哪批判定」。

**做法**：`tools/ops_export.py --task t_truth_pair --format jsonl --out <path>`，导出时写一个 manifest：`{task_id, item_count, label_max_id, exported_at, dialect}`，并把该文件登记为下一个 run 的 `dataset`（或 run 的 `params.inputs`）。

**验收**：导出的 jsonl 每行含 `item_id + value + annotator`；manifest 的 `label_max_id` 能反查「此后是否有新判定」——有则说明数据已过期。

### C 组 · 质量与回归（G5 G6 G7）

#### C1 · 双标与 kappa

**为什么**：`label` 表支持多 annotator，但实测只有 `legacy` 与 `console` 两个来源，**没有真正的双人独立标注**。所以现在算不出 kappa，也没有任何质量指标。

**做法**

- 抽样：`ops_sample.py --task <id> --rate 0.1 --to <annotator>` 从已判条目里抽 10% 生成"复核任务"（用 `annotation_item.stratum='audit'` 标记，不新建任务）；
- 计算：`ops_kappa.py --task <id>` 对同一 `item_id` 的两个 annotator 算 Cohen's kappa（多类用 Fleiss），低置信度条目列出来；
- 展示：总览加「标注一致性」KPI，低于阈值（建议 0.6）标红。

**取舍**：这需要**真的有人再判一遍**，成本落在人身上，不是代码。若不做双标，至少把「黄金题」（从已确认条目抽 5% 混入）做起来，成本低得多。

**验收**：抽 20 条由第二人判，`ops_kappa` 出 kappa 值与分歧清单。

#### C2 · 变体对比与回归

**为什么**：训练页只能看单变体曲线 + macro_f1 排序。看不出「v3 比 baseline 好在哪个机位、差多少」。

**做法**

- 后端：`GET /api/ops/train/compare?runs=a,b` 返回逐指标差值与 per-cam 差值；
- 前端：训练页变体表支持多选 → 对比面板（差值表 + 两曲线叠加）；
- 回归告警：新 run 入库时，若同 experiment 内有 baseline 且 `macro_f1` 低于 `baseline - 0.02`，在总览风险栏提示。

**验收**：任选两个变体，能显示 per-cam 差值；构造一个明显更差的 run，总览出现告警。

#### G7 · `experiment` 补假设与结论

**做法**：训练页批次卡片增加「假设 / 结论」两个可编辑字段（写 `experiment.hypothesis` / `conclusion`），并支持标记 baseline。

**验收**：3 个历史批次能补上假设与结论，刷新后保留。

## 3. 推荐执行顺序

| 批次 | 内容 | 理由 |
|---|---|---|
| **第 1 批** | A2 数据集登记 → A3 模型注册 → A1 stale 判定 | 三件互相依赖，做完才闭环；改动都在 `tools/` 新增文件 + 一列 schema，不碰前端 |
| **第 2 批** | B1 读切换 ✅ → G8 导出绑定 → B1 写切换 | 先让"唯一来源"成立，再谈下线老接口；每步可独立回滚 |
| **第 3 批** | C2 变体对比 → G7 假设结论 → C1 双标 kappa | 前三项是"看数据"，最后一项要人配合，放最后 |

**不建议并行第 1 批与第 2 批**：B1 写切换会让 `label` 表写入量上升，而 A1 stale 判定要读 `label` 的写入路径确认口径，同时改容易互相干扰。

## 4. 需要你定的一件事

**C1 双标要不要做？** 这是唯一「代码做完仍需人再判一遍」的项。

- **做**：抽 10% 复判，能得到 kappa 与分歧清单，标注质量第一次可度量；成本是约 **63 条** item 的人工复判（当前 633 条 item 的 10%）。
- **不做**：跳过 C1，用「黄金题」替代（从已确认条目抽 5% 混入队列，成本约 1/2），只能测出"标注员有没有认真"，测不出"两个人都判错"。
- **缓做**：先做 C2 与 G7，等有第二次标注需求时再上。

其余 A、B、C2、D 组都可以按上面的顺序自主推进，不需要再确认。
