## 1. 编码服务化：embed_server v1.1

**新增能力**（`tools/embed_server.py`，远程 crosscam_run/ 已部署，pid 常驻 GPU1，:8791）：

| 能力 | 说明 |
|---|---|
| `POST /encode_video_tracks` | **异步任务**：服务端自行"视频抽帧→裁剪(224²)→批量编码→均值→落 npz"；调用方只给 (video, jsonl, cam, prefix) |
| `GET /jobs` / `GET /jobs/{id}` | 任务列表/详情（进度、ETA、ms/图、结果）——轮询式，断连不丢任务 |
| 多 worker 并发 | 3 worker：解码(IO/CPU)与 GPU 编码重叠，GPU 串行由锁保证（FastEncoder 实例状态安全） |
| `/health` 扩展 | 队列深度/在跑数/累计 ms/图/jobs 总数 |
| `--jobs-log` | 任务完成 jsonl 追加（审计） |

**真实负载证据（长窗 3 路并发，18:05–18:40）**：

| 任务 | 轨数 | crops | 耗时 | ms/图（含竞争） |
|---|---|---|---|---|
| j1 316 | 149 | 829 | 678s | 32.0 |
| j2 318（旧口径，已废） | 478 | 3078 | ~1700s | 24.4 |
| j3 320 | 181 | 1179 | 573s | 23.9 |
| j5 318 修正版 | 496 | ~4100 | 1733s | 21.35 |
| j4/j6 补编码（318×4 / 305×1） | 4+1 | — | 17s/1.6s | — |

- 三路并发期间：GPU 串行吞吐 ≈ **30ms/图（含排队）**；单任务独占时 320 达 **23.9ms/图**——解码/编码重叠生效（对比单流 FastEncoder 19.7-20.1ms/图基线，竞争开销 ≤50%）。

**并发 N 客户端吞吐基准**（`svc_bench_remote.py`；32 crops/请求 × 8 请求/客户端）：

| clients | imgs | 吞吐 | p50 延迟 | p90 |
|---|---|---|---|---|
| 1 | 256 | 45.5 img/s | 703ms | 709ms |
| 3 | 768 | 48.1 img/s | 1993ms | 2003ms |
| 6 | 1536 | **47.9 img/s** | 3995ms | 4033ms |

→ **吞吐平台 ~48 img/s（≈20.8ms/图），1→6 客户端持平**：单客户端批量已使 GPU 饱和（RADIO 算力墙），并发只线性增加排队延迟。
服务价值 = **共享常驻 + 公平队列 + 异步长任务**（吞吐加成不来自并发堆叠——与 Phase 2 的"批量已饱和"结论一致）。

**运维**：常驻命令
```
cd ~/yhh/human-count/crosscam_run && nohup ~/yhh/human-count/embed_venv/bin/python embed_server.py \
  --port 8791 --device cuda:1 --w-dir cradio_scale_v4 --workers 3 --jobs-log embed_server_jobs.jsonl \
  --strip-dead > embed_server_v11.log 2>&1 &
```
> `--strip-dead`（2026-10-14 新增）：剥离 EmbeddingGemma2 未使用的 audio/vision 塔，
> 嵌入逐位不变（生产 A/B：重启前后同 4 图编码 bitwise 一致）、省 ~1.8GB 显存。
> 见 `docs/embgemma-strip-feasibility.md`；去掉该参数即回退全量装载。

## 4. 组合检索：嵌入 + 时空门控 + mutual-best

**问题**：v4 全库检索（8 个 318 查询 → 320 真配）：rank1 2/8、avg rank 4.00——失败项被"外观高分但时间/通道不可达"的干扰占位（如 (1,1) 被 316|113 压到 rank16）。

**方法**（`tools/combo_retrieval.py`）：门控窗来自 relay 通道拓扑实测（**不调参、不用测试集**）：
318↔320 同楼面重叠 ±60s；318↔316 门 ±60s（观测 1.4-18.5s）；318↔305 ±90s；318↔323 ±90s；318↔343 ±120s。
候选须与查询区间在扩展窗 [-D,+D] 有交集；C 模式再加"候选反向最佳 318 匹配 = 查询"的 mutual-best。

| 模式 | rank1 | avg rank | 候选库规模（8 查询） | 备注 |
|---|---|---|---|---|
| A baseline（全库 392） | 2/8 | 4.00 | 392 | 复现 v4_compare |
| B +时间门控 | 2/8 | **2.75** | 84–209 | (1,1) 16→6；**8 个真配全部保留** |
| C +mutual-best | 2/8 | **2.62** | **4–24**（最高 ~100× 剪枝） | (1,1) 6→5 |

**读法**：门控把"时间上不可能属于同一行程"的干扰批量剔除（avg rank 4.00→2.75），
mutual-best 进一步把候选压到个位数-几十（面向人工终审的队列长度直接可用）；
rank1 仍 2/8 的剩余错误为 (a) 同人双片段标签粒度（(120,23) 的 rank1 是同一人的另一片段）、
(b) 窗内强干扰（(69,14)/(139,24)/(146,28) 的 top-1..3 均为真实同窗人员，只是外观更像）。
→ 生产组合 = **门控检索（B/C）+ 复核队列**，与"自动候选+人工终审"既定策略一致。
