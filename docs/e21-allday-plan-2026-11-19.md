# E21 全天素材重估与长时窗方案（2026-11-19）

> 触发：用户指出 `/share/data4/yhh/human-count/{2026-10-22,2026-10-23,2026-10-26}/` 里「还有新的录像视频可以用」。
> 本文回答三件事：**那里到底有多少、E21 现有实验用掉了多少、多出来的部分能买到什么**。
> 全部数字为本轮实测（卷级解码 + OSD 目视 + GPU 吞吐），不引用旧文档的转述。

---

## 0 结论先行

1. **不是新机位，是新时长。** 三个目录一共 45 个 mp4，但物理机位仍是 **每天 6 路**；每个机位一天被切成 1–4 个 1 GB 续卷（`0100000` + 4 位卷号 + `00010000` 表示第 2 段）。合计 **88.1 机位小时**。
2. **E21 现有实验只用了 15.0 机位小时（17%）**，而且集中在每天一个 36–68 min 的「6 路交集窗」里。剩下 **73 机位小时** 从未被读。
3. 多出来的是**每机位 2–6.7 小时的连续覆盖**（不是碎片）。这正好补上论文最缺的一维：**小时级时间跨度**。D1/D2/E21 现有实验的最长连续窗都只有 35–68 min，「另一时间」的主张一直建立在 1 小时内。
4. **但它买不到真值。** E21 三天没有任何身份标注，跨机位也没有。所以：召回仍不可测，除非人工标簇（见 §4 P3）。任何「另一机位、另一件衣服」的**绝对精度**结论仍然只能来自 D1/D2。
5. 实测算力：原始 1440p HEVC + YOLO-seg(imgsz 960) + 跟踪 + OSNet，端到端 **≈15 采样帧/秒/卡**（stride 8）→ **4.8 s 视频/秒**。全量 88 h ≈ 18 GPU·h，双卡一夜可跑完；单机位全天 6 h ≈ 1.3 h/卡。

## 2 多出来的 73 小时能买到什么

### 2.1 能答（不需要身份真值）

| 问题 | 指标 | 为什么 36 min 答不了 |
|---|---|---|
| 长时窗下身份图会不会崩 | 簇数 / 簇大小分布 / **最大簇占比**（>25% 报警）/ fm 率 | 36 min 内一个人只进出 1–2 次，规模效应不出现 |
| 断口与重入的真实分布 | 同一机位内每人被切成几轨、断口时长分布 | 现有「中位 34 s 回来」是从 D1 35 min 窗推的，样本薄 |
| 人脸探针（P1）的可得率 | 有脸轨占比、可用脸中位像素随时间长度的变化 | 决定 L2/L3 能不能在部署里成立 |
| 报警判据的误报率 | 3 天 × 6 机位 = 18 次独立运行，报警触发次数的分布 | 单次运行只能给一个点，无法给「误报率」 |

### 2.2 能答（需人工标簇，2–3 h）

| 问题 | 产出 |
|---|---|
| 单机位全天身份真值 | 几百个簇里标出真实身份 → **第一次**有小时间级 + 跨天的簇级 GT |
| E2 写入收益在 Δt = 小时/天 尺度上的符号 | D2 的 19 次写入 → 全天可到 100+ 次，bootstrap 单元从 26 涨到 40+ |
| 召回的真分母 | 现有 E21 结论「召回不可测」被解除（限单机位） |

### 2.3 仍然答不了

- **跨机位身份真值**：三天都没有。共视搭桥在 D1 上给过 12 同 / 15 异（精度不够当 GT），这里不会更好。
- **「另一件衣服」的绝对精度**：跨天确实换装，但没有真值就没有精度，只能给**一致性**（同一套阈值在三天上是否给出同规模、同报警行为）。
- 因此论文里跨机位/换装的主张仍须标为「协议 + 组件证据」，不能写成实测增益。

## 3 算力实测（本轮，L20 46 GB）

| 环节 | 实测 | 说明 |
|---|---|---|
| 1440p HEVC 解码（ffmpeg → null） | 247 fps（默认线程）/ **638 fps（-threads 16）** | cv2 单线程只有 79 fps，是此前的隐性瓶颈 |
| NVDEC（`-hwaccel cuda`） | 418 fps | 比 -threads 16 慢，不用 |
| 解码 + scale 720p | 420 fps（ffmpeg 自读） | 但 **Python 逐帧读 pipe 只有 172 fps**，两进程各 41 fps |
| YOLO-seg 推理（imgsz 960） | **14.8 采样帧/秒** | 与基线等价：1440p→960 与 960×540→960 的网络输入相同 |
| 端到端（解码+跟踪+编码, stride 8） | **3.9 s 视频/秒/卡** | 实测（620 s 视频 / 82 s 墙钟），推理是墙不是解码 |

**成本**：1 h 素材 ≈ 0.26 卡·时 → 88 h 全量 ≈ **22.5 卡·时**（双卡 11 h）；单机位 6.1 h ≈ 1.6 卡·时；**三天单机位（P1，10 h 素材）≈ 2.6 卡·时，双卡约 1.3 h 墙钟**。

> 工程注意：管道的瓶颈是 Python 逐帧读 2.7 MB 的 720p 原始帧（~85 fps/进程）。改成 **960×540（1.55 MB/帧）+ `-threads 8`** 后单进程覆盖速率从 41 fps 升到 ~100 fps，端到端 3.9 s/s。若还要提速，下一档是「一次 read 多帧 + 分片」或把检测输入降到 imgsz 736（会损小目标，不推荐）。

**读法**：生产阈值（cos .78）下**过合并很少**（1.3% 的轨落在可证伪合并的簇里、最大簇只占 11%），
真正的形态是**过度碎片化**：一半的簇只有一条轨，最大簇 70 轨横跨 86 min。
阈值一放松到 .74，可证伪合并的轨占比立刻从 1.3% 跳到 27.7%——**没有安全余量**。
这与 D1/D2 的老结论一致（.75 更优但长卷否决），但这次是在**小时级**时间跨度上复现的。

**第二天独立复现（2026-10-26，1.7 h / 675 轨 / 404 轨每小时 / 中位轨长 7.0 s）**：
cos .78 → 139 簇、最大簇占比 .120、单轨簇 .468、**可证伪合并 0 簇 0%**；放松到 .74 → 2 簇 / 3.3%；
.66 → 3 簇 / 19.1%。两天都是“紧阈值几乎不误合、松一档立刻破防”的同一形态，
说明这不是单日的偶然。

**第三天（2026-10-22 全天 6.1 h / **1488 轨** / 307 轨每小时 / 中位轨长 5.1 s / 439 互斥对）**：
cos .78 → **224 簇**、最大簇 **223 轨**（占比 .150）、单轨簇 .495、可证伪合并 1 簇 / **0.2% 轨**；
.74 → 3.8%；.70 → 11.2%；.66 → 15.9%。
三点结论：①**时长翻 3 倍，误合几乎没有上升**（0% → 0.2%），说明生产阈值在小时级跨度上是稳的；
②但**最大簇开始逼近报警线**（.150 vs 判据 .25），且它横跨 2.5 h、223 条轨——这簇是不是一个人，
靠时间互斥判不了（从没同时出现），只能靠人工标簇回答；③轨道数随时长近似线性（307–404 轨/小时），
说明碎片化不是窗口长度造成的假象。

**先修正设计文档的两处硬错误（本轮 OSD 实测）**

1. **卷清单漏了 3 卷**，它们各自是一台相机的「续卷」，文档里被当成了终点：

2. **排除卷**：`3507p1`（与 `3507p0` 同起点 08:45:2x 的重复流，53.6 min）、`3484p1`（0.9 min 混编残卷）、`3515`（办公区2，~90% 灰帧）、`3415`（实为 10-22 的卷放错了日期目录）。

**同时改了两处代码口径**（`e21_allday.py`）

- **逐卷独立锚点**：spec 的 `vols` 支持 `[卷, 分段, "HH:MM:SS"]` 第三项。原版 `t = 锚点 + Σ前卷时长 + frame/fps`，遇到卷间缺口会整体前移——10-22 办公区2 两卷之间就有 16 min 缺口，用旧式会把 `3436` 的 5 小时全部错标。现在每卷以自己的 OSD 首帧为准。
- **框高回推倍率**：原 `h = (y2-y1) × 2.0` 只对 1080p 成立；1440p 缩到 960×540 是 ÷2.667。已改为按实际帧高计算，否则 1440p 机位的 `h` 系统性低 33%，`--min-h 60` 实际卡在 80 px。

### P3 人工标簇（已落到控制台）

**入口**：双击仓库根目录 `start-console.cmd` → 浏览器自动打开 `http://127.0.0.1:8010/#/e21-label`
（脚本会先起后端再开页面；关掉该窗口即停后端。也可以手动 `cd webapp/backend && python -m uvicorn main:app --port 8010`。）

**页面怎么用**
- 顶部选日期，进度条显示 已标/总数。
- **两种模式**：卡片网格（一次看几十个簇，适合快速扫）；**全屏标注**（一次一个簇、图放到最大，适合连续判读）。
  点右上「全屏标注」或按 **F** 进入，也可以直接收藏 `http://127.0.0.1:8010/#/e21-label?fs=1`。
- 每张卡 = 一个簇：4 张代表裁剪（最长轨、轨内 25%/75% 处）+ 簇号 / 轨数 / 时间跨度 / 中位框高。
- 同一个身份在输入框写**同一个名字**，回车或点「同名」；认不出是谁但确定不是人点「非人」；暂时判断不了点「跳过」。
- **单张图判非人**：每张裁剪下方（网格模式是图底部的小按钮）都能单独标「第 N 张：不是人」。
  这是**帧级**判断（这一帧检测错了），与整簇「非人」分开记——前者用来量检测假框率，后者是"这条轨不是人"，两者不能互相替代。
- **逐图命名（每张图不同身份）**：全屏模式下**每张裁剪图下面都有自己的小框**——打名字、回车，就只给这一张指派身份；
  四张图可以是四个人，互不影响。已指派的图右上角出现绿色姓名徽标，改判直接在框里改名再回车。
- **批量指派（一簇里两个人）**：**点图选中一张或多张**（选中亮蓝框，可多选、可全选）→ 在下方输入框打名字 → 点「标为「某某」」。
  被单独指派的图右上角会出现绿色姓名徽标，簇头部同时出现「混合」标签。改判用「撤销单图标注」回到继承簇标签。
  存储上簇标签是**默认归属**、单图标签是**覆盖**：`crops: {"0": "person:李四", "2": "reject"}`。
  CSV 新增 `n_crop_person` / `crop_persons` 两列（形如 `0:李四 1:李四`），可以按图重建真值。
- 全屏模式的键盘：`Enter` 同名并下一条 · `N` 整簇非人 · `S` 跳过 · `1–4` 单图非人 · `←/→` 翻页 · `Esc` 退出。
- 右侧「已用身份」列出已用名字与簇数，点一下就把该名字填进当前卡；「导出 CSV」给出簇级真值表（含 `n_crop`、`crop_reject` 两列）。

**为什么值得做**：单机位 + 全天时，**同一时刻的两条轨不可能是同一个人**（排除 IoU<0.2 的重复框）。
所以标完之后有两件事可以直接算，不需要再标到轨级：
1. **簇纯度**：某个被标为「张三」的簇里若含一对时间重叠且位置分离的轨，这个簇就是混了两个人——自动检出，不用人盯。
2. **碎片度**：同一个名字下挂了多少个簇、跨多长时间，就是"身份图把一个人切成几段"的直接度量（D1 的 5.5 轨/人 是同一件事的另一个口径）。
3. 附带：单图判非人给出的**帧级假框率**，可以对照属性线已知的 316/323/343 假框率 39.8/47.9/42.0%，检验办公室场景是不是同一量级。
