# R3 评分层实验：T-norm / AS-norm / 竞争簇校正 能不能推高覆盖

日期：2026-10-19 ｜ 性质：**已执行实验（离线，NumPy 后处理，无训练）**
输入：`output_crosscam_local/1012_yolo8_dd_emb`（579 gallery / 229 query，512 维）
脚本：`tools/eval_score_normalization.py`、`tools/check_norm_added_tracks.py`、`tools/eval_dual_gate.py`

## 1. 结论

1. **T-norm 确实把前沿推高了，而且统计显著**：same≥0.90 下覆盖 0.568 → **0.659**（+9.1pp），
   配对 McNemar 精确检验 **p=0.0025**（+33 / −12）。但 fm 从 0.75% 升到 **1.75%**（6→15 对）。
2. **增益的证据强度存疑**：新增接受的 33 条轨迹，绝对 top-1 余弦中位 **0.500**（base 已接受组 0.679），
   其中 **26/33 低于 base 组的 p10（0.534）**。它们不是"找到了更强的匹配"，而是"被 query 自身分布重新标定后越过了门槛"。
3. **加一道绝对余弦下限后，增益基本消失**：`tnorm + abs≥0.50` 覆盖 0.620、same 0.908、fm 1.20%，
   但配对检验 **p=0.0576**（不显著）；门槛提到 0.55，覆盖反而掉到 0.537（低于基线）。
4. **AS-norm 的覆盖更高但代价更大**（asnorm64：0.760 / same 0.902 / fm 2.69%），**越过 2% 预算**，不可直接采用。
5. 因此：**现在不能采纳**。判定权在那 33 条轨迹是真人还是错配——已导出 33 行清单，需 30–45 分钟人工目检。

## 4. 为什么 T-norm 的增益可疑

**绝对余弦（两片中较低的那片，保守口径）**

| 组 | n | p10 | p50 | p90 |
|---|---|---|---|---|
| base 已接受 | 130 | 0.534 | **0.679** | 0.800 |
| tnorm 新增接受 | 33 | 0.435 | **0.500** | 0.585 |
| tnorm 弃掉（原本接受） | 12 | 0.543 | 0.583 | 0.627 |
| 从未接受 | 66 | 0.305 | 0.412 | 0.539 |

新增组的绝对余弦落在"base 已接受"与"从未接受"之间，**26/33 低于 base 组 p10**。
即：T-norm 用 query 自身分数的均值/标准差做标定，会把"对所有簇都低分、但相对有峰"的轨迹抬过门槛。
`same` 抓不到这种错误（两片可以一致地选中同一个错簇），`fm` 也只能抓到其中撞上同帧他人的部分。

**支持"不全是错配"的两条反证**
- 33 条散落在 **14 个不同簇**，最大簇占 21%（若是一个"万能吸引簇"，会高度集中）；
- 按机位：320 占 15、323 占 8、305 占 6、318 占 4——集中在成像最弱、远场最多的 320，符合"真人也弱"的解释。

**支持"部分是错配"的一条反证**
- 误合并对数 6 → 15；新增 33 条里有相当一部分落进了"同帧有人"的簇。一个错配轨迹在繁忙场景可产生多对，故 15 对不等于 15 人错。

→ 结论：**五五开，必须目检**。清单已导出：`selector_osnet_1012/r3_audit_added_tracks.csv`（33 行，按绝对余弦降序）。

## 5. 顺带查清：弃判后为什么还有 0.26% 的 fm

不是 bug，是**口径粒度不一致**：
`eval_point` 的合并判定用 `acca[iu] & accb[iv]`（单侧接受即可计入分子），而覆盖要求 `acca & accb`（两片都接受）。
所以「只被接受一片」的轨迹仍可能构成一次合并，但它在覆盖里根本不计入，自然也不会被"弃判"处理。
→ 这意味着 **fm 的分子与 coverage 的分母不是同一批轨迹**。这不影响历史数字的横比，但解释时必须写明。

## 9. 附带改动：`eval_det_switch.py` 增加 `--fm-max`（可选，不改历史口径）

为消除 §5 的口径缺口（self-cal 不约束 fm），新增可选参数：

```bash
"$PY" tools/eval_det_switch.py --profile configs/selector_deploy.json --fm-max 0.02
```

- 默认不生效，历史数字不变（已验证：yolo8dd 仍为 0.568/0.908/0.75%，baseline 0.423/0.903/1.96%）；
- 加上 `--fm-max 0.02` 后，当前生产点不变（本就满足），但会排除 asnorm64 这类 fm 2.69% 的方案；
- profile 里若写 `"fm_max": 0.02`，自动生效。**是否写进 profile 属口径变更，需单独确认。**
