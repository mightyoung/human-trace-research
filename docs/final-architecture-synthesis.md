## 0. 结论先行

1. **六个系统的价值分级（对我们可以怎么用）**：

| 系统 | 性质 | 对我们的价值 | 级别 |
|---|---|---|---|
| **EmbeddingGemma 2**（我们已在用） | 多模态嵌入模型（官方 tech guide） | 组件级拆解**印证我们实现全部正确**（masked_scatter/mean-pool/512 宽接口）；**MRL 截断**可用于缓存压缩；**官方警告勿用 FP16**（印证我们维持 fp32） | ★★★ 直接可用 |
| **C-RADIOv4**（v3 的继任，我们已在用） | 组装式视觉主干（tech report 2601.17237） | 理解我们桥接上游的定位（dense features）；**SAM3 兼容分割可半自动生成反光掩膜**；ViTDet/多分辨率能力待查 | ★★★ 直接可用 |
| **Dream-RSI**（Google，2609.14858） | 探索策略元学习（非视觉系统） | **"历史即回放模拟器"→ 我们的判定/调度策略离线回放评估器**（方法论移植，非技术复用） | ★★★ 方法论 |
| **π0.7**（Physical Intelligence，2604.15483） | VLA 机器人基座 | **质量元数据条件化**（低质数据不丢弃）；知识绝缘（=我们冻结上游的纪律）；延迟容忍设计 | ★★ 工程映射 |
| **MiniCPM-V 4.5**（2509.18154） | 高效 MLLM | 3D-Resampler 帧组压缩（轨迹帧冗余）；快慢双档（粗筛/精编） | ★★ 可选探索 |
| **MOSS-VL-Realtime**（2608.15045） | 实时流式视频理解 | **主动沉默（观望态）+ 动态纠正（增量修订）→ 判定状态机设计**；视觉/语言解耦印证我们的异步编码架构 | ★★ 工程映射 |

2. **缓存选型结论（自研 vs Redis）**：**分阶段**——
   - **现在到 ~5 万轨：继续自研**（已验证 1.5KB/轨、0.2ms 检索、零依赖；远程服务器**无外网、无 Redis/faiss/qdrant**，Redis 引入需离线部署成本）；
   - **服务化触发条件**（多进程并发查询 / 在线增删 / 跨服务共享 / 持久化 SLA）出现时 → **Redis 8 Vector Sets**（原生 VADD/VSIM、内置 HNSW、部署轻量）；
   - 需要"结构化过滤+向量"混合检索时 → Redis Query Engine（FT.HYBRID、SVS-VAMANA+INT8 量化）；十亿级（本项目不可能）才考虑 Milvus。
   - **协同优化**：MRL 截断（768→256d）+ 量化 → 存储降 6–12×，适合"粗筛(256d)→精排(768d)"两级检索。

3. **最终架构一句话**：在已验证的单点能力（跨机 ReID AUC 1.0、接力 34 链、清洗 60/578 轨、FastEncoder 50 图/s）
   之上，补齐三层——**净数据地基（反光治理集成）→ 异步编码+缓存中台（FastEncoder+增量缓存）→ 观望态判定与回放评估闭环**，
   形成可服务化的完整系统。

## 1. 逐系统拆解与借鉴分析

### 1.1 EmbeddingGemma 2（Google，2026-10-06 发布；我们正在使用的嵌入器）

**组件级拆解（官方 tech guide 口径）**：

| 组件 | 官方参数 | 运行时含义 |
|---|---|---|
| 文本编码器 | 24 层、残差宽度 **512**、MLP 2048、gated-GELU | 每个 block 输入输出 `[B,S,512]` |
| 混合注意力 | **20 local + 4 global（5:1）**；local 半径 512 token；GQA(2KV/4Q) / global MQA(1KV/4Q) | 注意力开销 ≈ 20×O(S×1025)+4×O(S²)；非线性的残差项 |
| 位置编码 | RoPE base 10k（local）/ 1M（global） | 双频旋转 |
| 多模态桥 | 视觉/音频塔投影为 **512 宽 soft token**，`masked_scatter` 替换占位 token | 与文本共序列的 early fusion |
| PLE（逐层嵌入） | 投影式：输入一次投影到 `[B,S,24×512]`，每层取其切片，与层内 GELU 分支逐元素相乘再残差加回 | 每层可直接"查看"原始输入（**非** Engram 查表） |
| 输出路径 | per-token **512→768 投影** → mask-aware **mean pooling** → L2 归一 | 输出 `[B,768]` |
| MRL | 768 → 512/256/128 截断（截断后需再次归一化） | 只省索引存储/检索，不省编码计算 |
| 视觉 token 预算 | 图像 70/140/**280**/560/1120 档；帧 140/帧@1fps | 预算与文本共享 8K 上下文 |

**对我们实现的四项对照（全部吻合 ✅）**：
1. `masked_scatter` 替换占位——我们模板法的核心机制，与官方实现逐字一致；
2. **mean pooling**——我们实测三池化变体对照（mean_all 0.99995 ≫ mean_text 0.90 ≫ last 0.72）印证官方"mask-aware mean"；
3. **512 宽接口**——我们的 C-RADIOv4 桥接（1152→768→embed_vision→512）恰好落在官方设计的"512 宽 soft token"接口上：**这不是巧合，而是模型原本就是为"任意视觉塔投影进 512 宽"设计的**，我们实际上是把 C-RADIOv4 当作 EmbeddingGemma 官方的 vision tower 接口插了进去；
4. **精度**：官方明确 **"Use BF16 or FP32, not FP16"（激活范围超 FP16，会 NaN/静默劣化）**——印证了我们对语言塔"低精度无收益、维持 fp32"的决策是正确的（此前实测 fp16 未炸但收益为零，现在有了官方依据不再尝试）。

**新借鉴点（可落地）**：
- **MRL 截断**：缓存层存储 256d（省 3×），与"粗筛→精排"两级检索天然配套；对 128d 官方警告多模态退化明显（MMEB 45.65），**只用于文本粗筛或不用**。
- **视觉 token 预算档位**（70–1120）：我们当前 256 token/图（C-RADIO 桥接产出，接近官方 280 档）；若未来要降本，可试 140 档（但会损失细节，需评估）。
- **无 KV cache、每次全量重算**：官方明确这是编码器（双向、非因果解码）——我们的"批处理 + 缓存复用"策略正是对"重算贵"的正确补偿。

### 1.2 C-RADIO 系列（NVIDIA；我们使用的 C-RADIOv4 是第三代，用户所提 v3 为其前代）

**三代演进（组装式蒸馏路线的"怎么拆"）**：

| 代 | 教师组（拆解维度） | 解决的核心问题 |
|---|---|---|
| RADIOv2.5 | DFN-CLIP（语义）+ DINOv2（自监督稠密）+ SAM（实例） | "模式切换"——分辨率改变表征行为 |
| **C-RADIOv3**（CVPR 2025） | SigLIP2 替换 DFN-CLIP | 更强文本对齐；证明"零样本性能与整体表征能力可解耦" |
| **C-RADIOv4**（tech report 2601.17237） | **SigLIP2-g-384 + DINOv3-7B + SAM3** | 任意分辨率 + 高层推理效率 |

**v4 的关键技术（组件级）**：
- 学生 ViT：dense features 对齐 DINOv3/SAM3；summary tokens 对齐 SigLIP2/DINOv3；
- **分层蒸馏**：低层学 DINOv3（基础特征）→ 中层学 SigLIP2（语义）→ 上层学 SAM3（任务特化）；
- **随机多分辨率训练**（低区 128–432px，高区 512–1152px）+ FeatSharp 上采样对齐 + **shift-equivariant 损失**（防学生记忆教师的位置性噪声）+ MESA 正则 + DAMP 噪声注入；
- **角度归一化 summary loss**（防弥散度大的教师主导——DINOv3 曾压制 SigLIP2）；
- **ViTDet 混合注意力**（动态窗口，高分辨率推理提速，快于 SAM3 ViT-L+ 编码器）；
- 我们的用法：SO400M 变体（412M）、512 输入（低区上方）、dense spatial features（32×32→2×2 池化→256 token）→ 桥接。

**借鉴点**：
1. **SAM3 兼容解码器 → 反光掩膜半自动化**：v4 学生"drop-in 兼容 SAM3 解码器"，我们的玻璃区域/落地镜掩膜（此前 343 掩膜需用户手工圈改）可尝试用其 dense 特征+分割头自动生成草稿，人工只做复核。（待验证我们 trust_remote_code 实现暴露的接口）
2. **ViTDet 模式**：若实现里有窗口注意力开关，可再压 12.7ms/图 的算力墙（待查）；
3. **多分辨率能力**：256–1536px 强鲁棒——未来跨分辨率统一编码（远景小目标）有升级空间；
4. **token merging（v2.5 传承）**：若未来要降 token 预算，此为参考路线。

### 1.3 Dream-RSI（Google/DeepMind 等，arXiv 2609.14858）——"历史即回放模拟器"**

**先说结论：能借鉴，但要正确定位。**它不是视觉/加速技术，而是**"探索策略的元层优化"方法论**：把已完成的发现历史（决策树+执行结果）变成一个"回放模拟器"，任何新策略（分支/并行/停止时机）都可以在历史记录上零成本"梦境评估"，再部署回线上。定量：ConvDiv 内核任务同预算性能 2.09×；Lasso 317 vs 550 次调用（1.7×）；kernel 2.43× 更少世代。局限（论文自认+评述）：**重放只能覆盖已实现的历史**，不能产生历史之外的结果。

**对我们的映射（方法论移植，不是技术复用）**——**判定/调度策略的离线回放评估器**：
- 我们拥有海量"发现历史"：727 轨轨迹、30 判读对、60 条倒影标注、408 自然对照、relay 49 边/34 链、嵌入缓存（**策略评估不需要重跑模型——嵌入已在缓存里！**）；
- 任何策略参数（时间门阈值、相似度门限、深度复核分位、掩膜、调度顺序、缓存淘汰）都可以先在历史记录上"回放"打分，再上线；
- 这其实是现有纪律的自然延伸：我们的"**val 校准门限**"就是最小化的回放评估（单参数、单数据集）；Dream-RSI 把它推广为"**全策略回放**"（多参数组合、多指标、配置化）。
- 落地最小版：`配置 JSON → 回放脚本（读缓存嵌入 + 判定记录）→ 指标表`，复用现有 eval 工具即可，无需新模型。
- **不适用部分（诚实标注）**：它不解决任何推理加速问题；"递归自我改进"的叙事与我们的系统无直接关系，不要过度包装。

### 1.4 π0.7（Physical Intelligence，arXiv 2604.15483）——条件化与数据利用**

**组件拆解**：~5B（Gemma3-4B VLM + 400M 视觉编码器 + 860M action expert）；flow-matching 50 步动作块；**多模态 prompt = 语言指令 + 回合元数据（速度/质量/策略）+ 控制模式标签 + 世界模型生成的子目标图**；**知识绝缘**（action expert 梯度不回流 VLM 主干）；模拟 240ms 推理延迟下保持 50Hz 控制。

**可借鉴（工程映射）**：
1. **质量元数据条件化**：给我们的轨迹/crop 附元数据（检测分、目标尺寸、模糊度、反光场景标签、机位），低质量数据**标注后保留**用于难例分析与分层评估，而不是直接丢弃——与我们自训练"混合域平衡"的教训互相印证；
2. **知识绝缘 = 我们的冻结纪律**：自训练只动下游度量、不动上游桥接 W 与嵌入器（我们已在执行，获得方法论背书）；
3. **延迟容忍设计**：实时原型里"判定管线按最新可用证据工作、容忍编码延迟"——与 MOSS 的流式交互一致（见 1.6）。

### 1.5 MiniCPM-V 4.5（arXiv 2509.18154）——跨帧冗余压缩**

**组件拆解**：统一 3D-Resampler（可学习 query + 2D 空间/时间位置嵌入的跨注意力）——6 帧 448² **联合压缩为 64 token（96× 压缩）**；单图 64 token（对比主流 256）；1080 帧@10fps；训练时包大小/帧率随机增广（推理可调）；三阶段训练（仅 Resampler→视觉塔→全参）；Hybrid RL 快慢思考（推理耗时 42.9–68.2%）。

**可借鉴（可选探索，标注风险）**：
- 我们的轨迹采样 8 帧（同一人 2–3 秒内），帧间冗余极大——理论上可做"帧组联合编码"；
- **但注意**：我们的嵌入用途是**身份判别**（ReID），不是语义理解——过度压缩可能损失个体判别细节。建议作为"后续对照实验"（例如：验证帧组压缩嵌入在 30 判读对上的 AUC 是否保持），而非默认路径；
- **快慢双档**已部分存在：C-RADIOv4 的 summary token（快）vs 全链路（慢）——可用于两级检索的粗筛层。

### 1.6 MOSS-VL-Realtime（OpenMOSS/复旦，arXiv 2608.15045）——实时流式范式**

**组件拆解**：11.3B；**门控交叉注意力：视觉编码与语言推理解耦，视觉 token 不在解码序列中**（视觉上下文增大时 TTFT 优势 2.8×→5.1× vs Qwen3-VL-8B）；**XRoPE**（Time/Height/Width 统一坐标）；绝对时间戳帧；256K 上下文；SGLang 推理 4.57×。三种交互：**随时应答 / 主动沉默 / 动态纠正**（新证据到达时修订既有回答）。

**可借鉴（工程映射，直接进判定层设计）**：
1. **"主动沉默"→ 判定"观望态"**：证据不足时不下结论（保留候选、持续积累），例：置信度处于灰区（0.90–0.95）的匹配对进入 pending，等后续轨迹/慢轨证据；避免强行判定制造假匹配；
2. **"动态纠正"→ 增量修订**：新轨迹入库后，重算受影响的 pending/低置信判定（只扫时间窗内候选，代价可控）——缓存层已有 `add` 增量接口，判定层加"重算触发"即可；
3. **视觉/语言解耦 = 我们架构的背书**：FastEncoder 批编码（异步、与判定解耦）+ 缓存层按需消费，正是"编码不阻塞推理"的同构设计；
4. 绝对时间戳体系（我们的 OSD 时间 + 跨机 +0.8s 偏移）与该范式对齐。

### 1.7 扩展与补充（此前的调研遗产）

- **π0/π0.5 的 RTC（Real-Time Chunking）**：推理与执行重叠、前缀引导——我们已实测"无需显式流水（PyTorch 异步提交自带背靠背）"，RTC 思想在"编码批次与消费解耦"层面已落地；
- **vla.cpp 前缀 KV 复用 / FlashRT 低精度**：编码器场景不适用（无 KV cache；低精度已实测无收益）；
- **RADIOv2.5 token merging**：见 1.2。

## 3. 去镜像/倒影治理 × 前沿方法的对齐

**现状底账（已完成，勿重做）**：地板倒影运动学清洗（真对 28/29=96.6%，自然对照误过 1.7%）→ 六路 578 轨清洗 60 条（10.4%）；
墙镜玻璃掩膜（316/323 已启，343 草稿）；深度残差复核 AUC 0.931；翻转手性 AUC 0.798；组合拳定型（时间门→dt 分流→深度复核→几何审计→人工终审）；
dualclean 短名单 27 条；P1 清洗回流完成。**缺口**：集成未落地（7 个接入点，R4.1 已备好硬前提——检测源 md5 一致）。

**新对齐（本次调研新增的结合点）**：
1. **掩膜自动化（C-RADIOv4×SAM3）**：343 掩膜卡在手工圈改 → 用分割能力自动出草稿，用户只做确认（降人力）；
2. **反光场景标签（π0.7 式元数据）**：把"镜像候选/掩膜区/倒影判定"作为轨迹元数据入缓存——回放评估时可以按场景分层看指标（例：无掩膜区的假匹配率 vs 掩膜区）；
3. **观望态与倒影复核（MOSS 式）**：倒影判定中"证据弱"的轨迹（如短暂出现的疑似镜像）不断言，进 pending 随新证据复核——减少 408 自然对照里那 1.7% 的误杀风险；
4. **回放评估器（Dream-RSI 式）**：镜像规则的任何调整（阈值、组合权重）先在 437 个历史评估对（29 真对+408 对照）上回放打分——防止"调一个参数破坏另一处"的回归。

## 4. 缓存与向量存储：自研 vs Redis（决策级对比）

### 4.1 现状与规模测算

| 项 | 数值 |
|---|---|
| 现有规模 | 727 轨（六路 10 分钟）× 768d fp16 = **1.5KB/轨** |
| 自研检索实测 | **0.2ms/次**（numpy 暴力，全库 727）；支持 cam/时间/排除过滤 |
| 年规模外推 | 6 机位约 57GB/年（若全存 768d fp16、按现有轨迹密度外推——实际以"关键帧轨"计远小于此） |
| 服务化目标规模 | 数千～数万轨（几十 MB）——**很小** |

### 4.2 远程环境约束（实测）

服务器**无外网**；**Redis / faiss / qdrant / redis-py 均未安装**。引入任何外部存储 = 一次离线部署动作（Redis 静态二进制 ~2MB 可离线解决；Milvus 类则需 K8s/etcd/S3，完全不匹配）。

### 4.3 方案对比

| 方案 | 检索能力 | 过滤/混合查询 | 部署成本 | 并发/服务化 | 适配度 |
|---|---|---|---|---|---|
| **自研 npz+sqlite（现状）** | 暴力 0.2ms（<1 万轨） | 手写（够用） | **零** | 单进程 | ★★★ 现规模最优 |
| **Redis 8 Vector Sets**（VADD/VSIM，内置 HNSW） | ANN，亿级 | 轻量 JSON 属性过滤 | 低（单二进制，离线可部署） | **原生多客户端/持久化** | ★★★ 服务化首选 |
| **Redis Query Engine**（FT.CREATE/FT.HYBRID） | FLAT/HNSW/SVS-VAMANA + INT8 量化 | **全功能**（tag/数值/全文/地理 + 混合检索） | 中（模块化） | 原生 | ★★ 复杂查询时升级 |
| FAISS（本地库） | 最强 ANN 工具箱 | 无（应用层） | 低（但同样无外网安装问题） | 无服务 | ☆ 备选 |
| Qdrant / Milvus | 强 | 强 | 中/高（独立服务+集群） | 原生 | ☆ 不匹配（规模小、无外网） |

### 4.4 推荐（含触发条件）

**推荐：分阶段，现阶段保持自研；触发即升级。**
- **保持自研的条件（当前满足）**：总轨数 < 5 万、单进程消费、无需在线增删 SLA、暴力检索延迟 < 1ms；
- **升级 Redis 的触发条件（任一）**：① 编码服务与判定服务变成两个进程（并发读写）；② 需要在线增删/过期策略；③ 需要跨机位"元数据过滤+向量"一条查询；④ 要求持久化/热备；⑤ 轨迹数 > 5 万或检索 > 100 QPS（届时 HNSW 才有意义）。
- **升级路径**：`npz+sqlite → Redis Vector Sets`（一步到位，VADD/VSIM 与原 API 语义几乎一一对应：add→VADD、search→VSIM、attrs→SETATTR）；仅当需要复合过滤时再上 Query Engine。
- **存储协同（立即可做，无需 Redis）**：**MRL 截断 768→256d**：存储 1.5KB→0.5KB（3×），"粗筛 256d → 精排 768d"两级检索（精排仍用全量嵌入）；配合 fp16 已有（Redis 路径还可 INT8）。
- **取舍说明**：为什么不直接上 Redis？——数据小（几十 MB）+ 无外网 + 零依赖现值，Redis 的增量价值（并发/服务化）当前用不上；等到用得上时，迁移成本很低（接口一一对应），**不是"不选"，是"排序"**。

### 5.1 分层架构

               ▼

               ▼

               ▼

## 7. 附：一句话回答用户的四个问题

1. **Dream-RSI 能借鉴吗？** 能——把"判定/调度策略的调优"变成"在历史记录上的零成本回放评估"（它不解决加速/建模，解决的是**策略迭代效率**）；
2. **EmbeddingGemma 2 / C-RADIO 的论文怎么拆解？** EmbeddingGemma 2 = 文本塔（24 层×512）/多模态桥（512 宽 soft token）/输出路径（512→768+mean pool+MRL）三段；C-RADIO = 教师组（SigLIP2+DINOv3+SAM3）×学生（dense/summary 双对齐）×蒸馏技术（shift-equivariant/MESA/角度归一化）三层——**我们实现的两个关键选择（mean pool、512 宽桥接）与官方设计逐字吻合**；
3. **π0.7/MiniCPM/MOSS 借鉴什么？** 元数据条件化（π0.7）、帧组压缩与快慢档（MiniCPM，需对照）、观望态+动态纠正+视觉语言解耦（MOSS，直接可用）；
4. **缓存自己写还是 Redis？** 现在自研（0.2ms 已够、无外网零依赖）；服务化触发即迁 Redis 8 Vector Sets（迁移成本低，接口一一对应）；MRL 截断立即可做。
