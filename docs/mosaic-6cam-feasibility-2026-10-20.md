# 六路画面拼接送模型 —— 可行性研究

**日期**：2026-10-20 ｜ **性质**：可行性实测（本机 CPU，非生产 GPU 环境）
**问题**：把 6 路画面拼接为一张大画面（像素不减少），输入模型判断是否可行。
**数据**：`media-resource/multi-cemra/synced-10min`（2026-10-10 08:55–09:05，6 路同步，t=300 s 帧）
**模型**：YOLO26s-seg（生产检测器），`device=cpu`
**脚本**：`tools/mosaic_feasibility.py`、`tools/res_recall_curve.py`、`tools/batch_vs_mosaic.py`
**产物**：`output_crosscam_local/mosaic_feasibility/`

---

## 0. 结论

**不可行。** 三个独立的否决条件，任一成立即可否定：

| # | 否决条件 | 实测依据 |
|---|---|---|
| 1 | **"像素不减少"与"模型能吃的输入尺寸"互斥** | 严格保像素需 `imgsz=7680`（22.12 MP），实测 **19.25 s/帧**，比对等像素的逐路方案慢 **2.6 倍** |
| 2 | **拼图不产生任何跨路信息** | 6 路是 6 个不连续空间（无共享视野），拼贴只是并置；YOLO 是局部卷积，无跨区域关联机制 |
| 3 | **"合并成一次输入"在 CPU 上整体失败** | 逐路串行 1.76 s ＜ 拼图 2.61 s ＜ batch=6 3.74 s；合并输入没有一种形式更快 |

**唯一有意义的读法**是"几何全景拼接"（按相机外参把重叠视野融合成连续画面），但 6 路中只有 **318×320** 一对有真实重叠，其余 4 路物理上无法拼成连续画面。而 318×320 的重叠区去重已用单应映射解决（AUC 1.000），不需要拼大图。

---

## 1. 两种"拼接"必须先分开

| 读法 | 定义 | 本项目的可行性 |
|---|---|---|
| **网格拼贴**（mosaic） | 6 路排成 3×2 放进一张画布，各路内容互不连续 | 技术上能做（`six_stream_parallel.py` 已做输出侧展示），但对模型无信息增益 |
| **几何全景**（stitching） | 按相机外参/单应，把有重叠的画面融合成一张连续大图 | 只有 318×320 可行；其余 4 路无重叠，物理上拼不出来 |

本文测的是第一种。第二种的结论在 §5。

## 2. 像素账本

| 项 | 数值 |
|---|---|
| 316 / 305 / 320 / 343 | 4 × 2560×1440 = 14.75 MP |
| 318 / 323 | 2 × 1920×1080 = 4.15 MP |
| **原生合计** | **18.89 MP** |
| 3×2 画布（单元 2560×1440） | 7680×2880 = **22.12 MP**（黑边 3.23 MP，占 17%） |
| 生产 6 路合计输入（每路 imgsz=1280） | 6 × 1280×720 = **5.53 MP** |
| 拼接保原生 / 生产合计 | **4.0 倍** |
| 拼图压到 imgsz=1280 后每路 | 426×240 = 0.102 MP = 生产单路的 **1/9** |

关键矛盾：模型输入尺寸是一个定值（生产 `imgsz=1280`）。"像素不减少"要求画布 22.12 MP，模型就必须吃 22.12 MP；一旦模型把长边压回 1280，每路只剩 426 px 宽 —— **"像素不减少"的前提在进入模型的那一刻就失效了**。

## 3. 实测：同一帧（t=300）的四种输入形式

| 方案 | imgsz | 每帧耗时 | 检出数 (conf≥0.10) | 逐路明细（316/305/318/320/323/343） |
|---|---|---|---|---|
| **逐路串行**（生产现状） | 1280 | **1.76 s** | **14** | 0 / 5 / 4 / 0 / 5 / 0 |
| batch=6（一次 forward） | 1280 | 3.74 s | 19 | 0 / 6 / 6 / 0 / 7 / 0 |
| 拼图 3×2 | 1280 | **0.24 s** | 8 | 0 / 4 / **0** / 0 / 4 / 0 |
| 拼图 3×2 | 3840 | 2.61 s | 15 | 0 / 5 / 6 / 0 / 4 / 0 |
| 拼图 3×2（严格保像素） | 7680 | **19.25 s** | 13 | 0 / 5 / 4 / 0 / 4 / 0 |

读数：

1. **严格保像素的代价是 19.25 秒/帧**（0.05 fps）。同一帧逐路原生（每路 imgsz≈2560）约 6 × 1.45 s ≈ 8.7 s，**拼图贵 2.2 倍**。多出来的开销是黑边（17%）+ 大图内存带宽效率低。
2. **拼图压到生产等效分辨率**（imgsz=3840，每路 1280×720）：2.61 s，比逐路 1.76 s **慢 48%**，检出 15 vs 14（差 1 条，无统计意义）。
3. **拼图压到单路预算**（imgsz=1280）：只要 0.24 s，但 **318 从 4 条掉到 0**，总检出 14→8（**−43%**）。原因是 318 是 1920×1080 源，放进 2560 单元后占 75% 宽，再整体压 6 倍 → 实际只有 320×180，工位上的人直接消失。
4. **batch=6 在 CPU 上更慢**（3.74 vs 1.76 s，**2.1 倍**）。16 个逻辑核已被单图 forward 吃满，多图并行只增加内存带宽争抢。检出数反而 19 > 14，是低阈值（0.10）附近数值路径差异导致的边界框翻转，不代表真实召回提升。

> 检出数为 0 的路（316/320/343）经画面确认当时确实无人，不是漏检。

## 4. 为什么拼图不产生信息增益

**4.1 YOLO 没有跨区域推理能力。**
检测头是逐位置分类 + 回归，特征图上的每个位置只看局部感受野。把 6 路并置在一张 canvas 上，与分 6 次送进去，在数学上等价（都只做逐图逐位置预测），区别仅在于 batch 维还是空间维。空间维还要多付黑边与对齐成本 → 严格劣于 batch。

**4.2 训练尺度先验不匹配。**
`train_yolo.py` 默认 `imgsz=960`，生产推理用 1280（1.33 倍外推）。拼图要 7680，是训练尺度的 **8 倍**。虽然 FCN 理论上尺度无关，但 anchor 匹配、损失归一化、NMS 的先验都按训练尺度标定，8 倍外推会让"目标相对尺度"整体左移，实际退化 —— 实测 7680 检出 13 条，比逐路 14 条**还少**，未观察到任何增益。

**4.3 六路是六个不连续空间。**
`grid_t300.0.jpg` 目检：316 行政走廊、305 办公区1、318 办公区2（不同朝向）、320 球机俯视鱼眼、323 茶水间走廊、343 电梯间。除 318×320 一对，**没有任何两路共享视野**。拼贴不创造空间连续性，"一张图看全楼"在几何上是假的。

**4.4 均匀网格是错误的分辨率分配。**
343 电梯间整段无人，却和 305 密集办公区（5 人）分到同样 2560×1440 的画布面积。拼图把算力平均分给"感知需求极不均匀"的 6 路，这是结构性的浪费。

## 5. 什么情况下拼接是有意义的

| 条件 | 说明 |
|---|---|
| **A. 几何全景（真拼接）** | 需要相机外参 + 重叠区单应。本项目只有 318×320 满足；已有映射 AUC 1.000，做重叠区去重不需要拼大图，直接投影 + 最近邻即可。 |
| **B. 有 NVIDIA 大显存 GPU** | 拼图能把 GPU 利用率拉满（大图比小图更喂饱 SM）。估算 A100 80G 上 7680 输入约 200–250 ms/帧（**未实测，按面积线性外推**），显存约 30–36 GB。仍达不到 6 路 25 fps 实时，但可作为离线批处理方案。 |
| **C. 只做"有没有人"的快速筛查** | 拼图 imgsz=640 → 每路约 213×120，实测 0.1 s 量级。能判断"这一秒哪几路有人"，不能给出可用框。这与"像素不减少"前提矛盾。 |
| **D. 训练一个专门的"多路联合"模型** | 需要 22 MP 输入的训练数据与显存，公开数据无此分布；本机无 GPU，不可行。 |

---

## 6. 替代路径（按性价比排序）

1. **保持逐路推理 + 后融合**（现状）。本机 CPU 上它已是最快的形式，像素零损失。
2. **不要用 batch 去"合并输入"**。CPU 上 batch=6 慢 2.1 倍；GPU 上 batch 才有意义（需实测）。
3. **按需分配分辨率**：无人/低活动机位（343）降到 640，有人的机位保 1280–1920。省下的算力给 323 这类远场机位。这是"拼图想解决的问题"的正确解法。
4. **远场补齐走检测器而不是拼图**：323 的短板是远场小目标（s-seg 远场 25%，l-seg 100%），已证 `l-seg` 只在 323 有效（0.294→0.739），代价是全局 fm 翻倍。若要单独提升 323，应做**单机位专用检测器**，而不是拼一张大图。
