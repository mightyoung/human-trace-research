# 外部研究稿核对与合并：火焰/烟雾识别

日期：2026-10-19 ｜ 对象：外部 agent 提交的《火焰识别与烟雾识别：技术难点、近邻研究与实现路径论证》
性质：**核对 + 采纳 + 修订**，不重写原稿；结论以本文为准，原稿保留作参考。

---

## 0. 结论

1. **总体采纳。** 原稿把课题拆成"火焰 / 烟雾"两条独立研究线，并给出 F1–F3、S1–S4 的任务分解，比我们此前的"候选—疑似—确认"状态机更准确：**它把"看见火"与"判断危险"分开了**，这是概念上的实质改进。
2. **四条关键引用经核对属实**：SmokeyNet 两帧 F1 **82.59%**、平均发现时间 **3.12 min**；FLAME（2025）运动过滤使 Precision **+18pp**、F-Score **+10pp**、检测延迟翻倍、平均 **9.17 s**；FalseNet（IEEE Access 2025）覆盖蜡烛/壁炉/燃气火盆/LED 等良性火源；Spot 热辐射场（arXiv 2602.19108）用于**热安全导航**。
3. **三处表述需校正**：移动机器人级联是 **500 mm** 安全距离（不是 0.5–1 m）；SmokeCPC 的 61.83 是 **NSIoU**（不是普通 IoU）；SmokeBench 的 WACV 2026 出处**未核实**。
4. **它对我们旧文档提出六处有效反驳**，已全部采纳：HDR 不应预设关闭；面积增长/质心向上不能当硬规则；机器狗高置信目标可在运动中先预警；误报削减系数不是独立乘法；应双时间尺度并行而非单次 burst；时延应从"首次可见条件"起算。
5. **合并后议程为 U1–U13**（§6），P0 五项：现场盘点、采样率实验、火焰/良性火源鉴别、早期弱烟检测、单帧误报率下限。

## 2. 原稿的实质增量（我们此前没有的）

### 2.1 任务分解：从"置信度状态机"到"语义分层"

| 原稿 | 我们旧文档 | 为什么原稿更好 |
|---|---|---|
| F1 火焰候选检测 | candidate | 只回答"像不像火" |
| F2 火焰真实性 | suspected/confirmed | 回答"是不是真燃烧"，排除屏幕/反光/LED |
| F3 危险火情评估 | 无 | 回答"是否异常"，需要作业许可、位置、工艺上下文 |
| S1 存在性 / S2 弱定位 / S3 时空演化 / S4 干扰鉴别 | 单一"烟雾"类 | 四个子任务的评价口径不同，不能合并成一个 mAP |

**直接后果**：事件 schema 需要新增 `flame_presence`、`flame_authenticity`、`hazard_assessment`（hazard / benign / **unknown**）、`smoke_presence`、`smoke_evolution`、`discrimination`（smoke / steam / dust / unknown）、`evidence_sources[]`、`permit_ref`。

**关键点**：危险性判断不了时必须输出 `unknown`，**不能默认安全**。这是我们旧 schema 缺的。

### 2.2 采样覆盖概率

原稿给出 `P_capture = min(1, D/T)`，并指出"已持续燃烧的火焰 5 s 轮询不一定漏，只增加等待"。这两点都对，且比我们此前"5 s 轮询会丢闪烁"的定性说法更精确。

补充两条：
- **平均等待 = T/2**（均匀相位假设）。5 s 轮询的平均首见延迟是 2.5 s，不是 5 s。
- **周期性与轮询同频时公式失效**：若某设备每 5 s 周期性喷火，而相机也每 5 s 采样，可能恒中或恒漏。工程上应加随机抖动（jitter）。

已加入工具：`python tools/fire_capacity_calc.py capture --table`。

### 2.3 双时间尺度

原稿主张"秒级短期证据"与"十秒–分钟级长期证据"并行，而不是"2 s burst 后做最终判断"。这比我们旧方案好：**弱烟候选可以先形成内部预警，同时继续积累证据**，不必等烟羽长大才承认它存在。

采纳后的形态：
- 短窗（1–5 s）：存在性、局部对比、多帧持续；
- 长窗（10 s–5 min）：背景变化、烟羽轨迹、扩散趋势、环境上下文；
- 两路证据并行进入融合，不互相阻塞。

### 2.4 机器狗的"主动视觉感知"

原稿提出 Active Visual Perception：模型不确定时，机器人应选择"下一次观察动作"（转向、靠近、停步、换角度）以最快获得有区分力的证据。这是我们此前没有的研究角度，且与固定机位形成真正的技术区别。

工程上可先做简化版策略：
1. 置信度落在灰区 → 停步稳像 1 s 重测；
2. 仍不确定 → 偏航 ±20° 换背景再看一次；
3. 仍不确定 → 上报"证据不足"，不报警。

### 2.5 良性火源类别

FalseNet 把"真实燃烧但正常"的场景单列：蜡烛、壁炉、燃气火盆、LED 火焰。我们此前的负样本桶只有"非火干扰"，缺了这一类。**这类样本不能标成负样本，也不能标成正样本，必须是第三类**（benign flame）。

### 2.6 误报相关性

原稿指出：不能假设单帧误报独立、再乘一个固定削减系数。这是对我们计算器 `--confirm-factor` 的正确批评。已改为"等效值"，并在输出中加注：**必须用连续录像回放实测**。

### 2.7 时延口径

原稿主张从"目标首次达到约定可见条件"起算，未检出的事件计入漏检。这比"模型首次检测到"更严谨，也解决了跨系统不可比的问题。采纳为一级口径；有点火真值时，另报"点火相对时延"。

### 2.8 传感器融合逻辑

原稿反对"任意两种传感器同时触发才报警"，主张高后果事件单强证据即可预警。这比简单的 N-of-M 规则更合理。采纳为决策层原则：**证据强度 × 后果严重度**，而非固定与门。

## 3. 需要校正的三处

| # | 原稿 | 校正 | 影响 |
|---|---|---|---|
| 1 | "0.5–1 m 小火源" | 论文写的是 **500 mm 安全距离**；平台为 Raspberry Pi + RGB/NIR 的移动机器人，非四足 | 不能据此推断机器狗在 3–5 m 的性能 |
| 2 | "SmokeCPC 61.83% IoU" | 指标是 **NSIoU**（normalized spatial IoU）；F1 75.26；FPR 0.28% 是**图像级** | 与普通 IoU 不可横比 |
| 3 | "SmokeBench（WACV 2026）" | arXiv 2512.11215 可查，**venue 未核实** | 引用时写"arXiv 2025" |

另有两处措辞建议：
- "FLAME（2025）"应写全 **Gragnaniello et al., Neural Computing and Applications 2025**，避免与 FLAME/FLAME2 无人机数据集混淆。
- "FalseNet 90.44%"是**视频分类**的 Acc/P/R，不是检测 mAP；引用时注明任务类型。

## 4. 与我们旧文档的六处冲突及裁决

| # | 旧文档 | 原稿 | 裁决 | 理由 |
|---|---|---|---|---|
| 1 | 机器狗"关 HDR 是硬性要求" | 应比较 AE / 锁定 / HDR，不能预设 | **采纳原稿** | 火焰高光与逆光场景下 HDR 可能保背景；必须实测 |
| 2 | 面积增长 >1.2 且质心向上作为确认硬门 | 通风/横风下烟可横向、向下、间歇，只能作正向证据 | **采纳原稿** | 园区有排风扇、穿堂风；硬门会漏 |
| 3 | 停步→稳像→复检→才报警 | 高置信可在运动中先预警，停步只为提高证据质量 | **采纳原稿** | 报警延迟比证据完美更重要；狗的安全状态另管 |
| 4 | 误报削减 30×/200× 作为计算系数 | 误报时空相关，不能独立相乘 | **采纳原稿** | 已改为"等效值 + 必须回放实测" |
| 5 | 候选后 2 s burst 做最终判断 | 短窗与长窗并行，不互相阻塞 | **采纳原稿** | 弱烟需要长窗，短窗会过早否决 |
| 6 | 时延从点火/首次检测起算 | 从"首次达到约定可见条件"起算，漏检计入漏检 | **采纳原稿** | 跨系统可比；点火真值难得 |

**未采纳的一条**：原稿建议"火焰与烟雾不应预先规定同一个检测头/权重"。这条方向正确，但我们不建议现在就拆成两套模型——**应先由 U8 对照实验决定**（统一检测器 vs 分离检测器 vs 共享骨干双头）。在数据量不足时，分离训练会让两个分支都欠拟合。

## 5. 对架构的影响

原稿的两分支 + 证据层 + 事件管理，替换我们此前的单链四层：

```
场景输入（园区抓图 / 狗相机+IMU+可选热像）
        ↓
预处理与质量评估（模糊/脏污/过曝/时间戳/ROI）
        ↓
┌───────────────┬───────────────┐
│ 火焰分支       │ 烟雾分支       │
│ 检测→真实性→热 │ 存在→弱定位→演化│
└───────────────┴───────────────┘
        ↓
证据融合与风险决策（证据强度 × 后果严重度；允许 unknown）
        ↓
事件管理：候选 / 疑似 / 已确认 / 已排除 / 证据不足
```

与旧架构的差别只有三处，但都关键：
1. **火焰与烟雾分支可共享骨干，但输出与阈值独立**；
2. **`hazard_assessment` 是独立字段**，不是置信度的别名；
3. **`unknown` 是合法终态**，不是"待定"。
