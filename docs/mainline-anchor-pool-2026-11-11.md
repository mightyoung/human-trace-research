# 人脸锚点「暂存类」+ 选择器实时值：可研评估（2026-11-11）

> 提案（用户）：检测全身时同时检测人脸；人脸若匹配到库中某身份，就把对应全身目标放进
> **暂存类**（不参与聚类），并在**身份选择器**里给该身份追加一份**实时特征值**，辅助实时判定与历史训练。
>
> 本文只做三件事：**测它的天花板、找它的边界、给出可落地的结构**。
> 脚本 `tmp/full/exp_anchor_pool.py`（远端跑）。数据：8 段 / 445 具名轨 / 26 身份 / OSNet-x1.0。

## 0. 结论

1. **方向成立，但增益有明确上限**：在「上午建库 → 下午推理」的同机位跨时段场景，
   注入实时锚点后选择器在**同精度下覆盖 +6 pt**（τ0.80：47%→53%，same 89.1%→90.4%），
   在松阈值下 +7 pt 覆盖且 same 还高 3.3 pt（τ0.75：69%/80.7% → 76%/84.0%）。
   这是**上限口径**（假设人脸匹配 100% 正确）。
2. **它治的是「同机位跨时段漂移」，不是跨机位**。同一个人的脸和身体在同一台相机的同一时段内，
   余弦中位 0.861（≥0.80 命中 67.3%）；上午库原型只有 0.770/40.8%。而跨机位这一层，
   31 条必需桥里 **0 条两端有可用脸**——这个机制完全够不着。
3. **真正的瓶颈是 323**。各机位可用脸比例：305 **19.9%** / 318 8.9% / 320 6.0% / **323 3.9%**。
   323 恰好是承载 22/31 条桥的枢纽机位 → 池子里最难的那部分，锚点帮不上。
4. **必须解决「两个真相源」**：锚点不进聚类，库就不更新；库不更新，锚点与库会越走越远。
   需要一条**晋升规则**（见 §4.3），否则选择器会在两个自相矛盾的原型间摇摆。

## 1. 一个先要说清的事实：脸在框内，不是「同场推断」

提案里「人脸匹配上 → 把这个人的全身目标放进暂存类」这句话，实现上比听起来更强：
**人脸框是人体框的子区域**，所以「脸 → 身份」直接标注的是**这一条轨本身**，
不需要任何时间窗或同场推断。时间窗只用于**向外扩散**（用锚点原型去判同一机位、附近时段的其它轨）。

这决定了机制分两层，收益完全不同：

| 层 | 作用范围 | 精度 | 覆盖率 |
|---|---|---|---|
| **直接标注**（脸在自己框里） | 该锚点轨本身 | 极高（= 人脸匹配精度） | 445 轨里 **54 条 = 12.1%** |
| **原型扩散**（实时值判别人） | 同机位 ±30 min 内的其它轨 | 中（取决于外观） | 下午查询里 **24.9%** 能找到本人锚点 |

★ 12.1% 是**具名 445 轨**上的比例（这批轨更长、更靠前）。全量 1178 轨上可用脸只有 **6.5%**，
所以生产里的直接标注覆盖要按 6.5% 估，不能按 12.1%。

## 2. 实测：实时锚点能不能抵消漂移

口径：上午 4 段（train）建原型库（每身份 = 该身份轨嵌入均值），下午 4 段（test）作查询，
共 197 条查询（其身份在库里有原型）。锚点 = 同机位、|Δt| ≤ 30 min、有可用脸、同身份的其它轨。

| 指标 | 上午库原型 | 同机位锚点原型 |
|---|---:|---:|
| 本人余弦 中位 | 0.770 | **0.861** |
| 本人余弦 ≥0.80 命中 | 40.8% | **67.3%** |
| top-1（候选 = 该窗口有锚点的身份，中位 3 个） | 32.7% | **100.0%** |

★ top-1 100% 不是平凡结果（候选集中位 3、最大 4），但它有**先验加成**：候选集本身
已经限定为「这个窗口里露过脸的人」。所以**不要用这个数对外**，用下面的选择器口径。

### 选择器口径（候选 = 全库 26 个身份，这才是真实场景）

| τ | 全库原型 cov / same | 库+锚点 cov / same | 变化 |
|---|---|---|---|
| 0.60 | 100% / 65.0% | 100% / 69.5% | same **+4.5** |
| 0.70 | 89% / 70.9% | 91% / 74.9% | cov +2，same +4.0 |
| 0.75 | 69% / 80.7% | **76%** / **84.0%** | cov **+7**，same +3.3 |
| 0.80 | 47% / 89.1% | **53%** / 90.4% | cov **+6**，same +1.3 |
| 0.85 | 25% / 94.0% | 29% / 94.7% | cov +4，same +0.7 |

**读法**：增益是「同精度下多判 6–7 个点」，而不是「精度大涨」。它的量级与步骤 2 的
ΔR（+3.93 pt，CI [+0.90,+11.08]）相当，但作用在**另一个环节**（选择器而非聚类），
理论上可叠加。

## 3. 边界：它救不了什么

1. **跨机位**：0/31 桥两端有脸。锚点对跨机位召回**贡献为 0**，别把它算进「搭桥」预算。
2. **323 枢纽**：可用脸 3.9%，而它涉及 22/31 条桥。这是结构性的（反光 + 剪影 + 朝向）。
3. **覆盖率上限**：24.9% 的「能受益查询」是在 445 具名轨上测的；按全 1178 轨的 6.5% 可用脸，
   机会会按比例缩水。真值要等全量重跑。
4. **反面风险**：一条错脸锚点会污染该身份的实时原型，且**污染会随时间窗扩散**。
   所以锚点必须带 `self_cos` / `pd` / 帧数门槛，且**可撤销**（这正是「不进聚类」的价值）。

## 4. 建议的结构

### 4.1 AnchorPool（暂存类）

```
AnchorPool                       # append-only，与 cluster 库物理隔离
  key   = (pid, cam)             # 按身份×机位分桶
  entry = { t_abs, emb, face_vec, self_cos, pd, box_h, track_key, src }
  ttl   = 2 h                    # 只服务「附近时段」，过期即失效
  query(pid, cam, t, W) -> 加权均值原型（权重随 Δt 衰减）
```

三条硬规则：
- **只写不删**（除 TTL），**绝不回写 cluster 库**；
- 每条 entry 必须能追溯到 `track_key` 与原始帧，便于事后撤销；
- 同一 `track_key` 只保留最高质量的一条（避免同一人刷爆池子）。

### 4.2 选择器注入（三处，按收益排序）

| 注入点 | 形式 | 收益来源 | 风险 |
|---|---|---|---|
| **A. 原型刷新** | `proto = normalize(w_lib·lib + w_live·anchor(t))`，`w_live` 随 Δt 衰减 | 实测 +6～7 pt 覆盖 | 错脸污染 |
| **B. 直接标注** | 锚点轨跳过外观判定，直接给身份（可仍走 unknown 拒判） | 12.1%（生产 6.5%）轨免判 | 错脸直接错标 |
| **C. 同帧否决** | 与锚点同帧共现的轨，候选里剔除该身份 | 与既有 cooc 约束**部分重复**，增量小 | 嵌套框误判 |

★ **C 的增量要谨慎**：聚类里的「同帧 ≥10 帧否决」已经挡住了大部分同簇合并，
选择器再加一层否决，边际收益接近 0。**优先做 A，其次 B，C 可先不做。**

### 4.3 晋升规则（避免两个真相源）

- 锚点身份在 **N 天内稳定命中同一 cluster**（建议 N=3、命中 ≥5 次）→ 才允许写回 cluster 库；
- 否则锚点与库冲突时，**以库为准、锚点只做排序加权**，并记一条冲突日志供人工看；
- 冲突率按机位统计——**323 的冲突率会是判据**：若 323 冲突率 >20%，说明该机位的脸不可用，
  直接对其关闭锚点。

### 4.4 历史训练

锚点能给的是**域内正样本对**（同机位、同时段、跨时段都有），这正好补上「A 路线止于身份数不够」的那个缺口的一半：
它不能增加身份数，但能增加**每个身份在目标域内的样本**。建议先只做**线性头**（不碰骨干），
并且必须**留身份**评测（这是 A 路线的教训）。

## 5. 建议的下一步（带停止条件）

**做一次端到端小实验**，不要先写工程：

1. 在 8 段上实现 AnchorPool（内存版即可）+ 注入点 A、B；
2. 指标用项目主口径：**P≥0.95 下的身份完整度**，基线 = 步骤 2 的 `R 0.3839 / 宏 47.2%`；
3. 同时报选择器口径的 `coverage / same`（τ=0.75、0.80 两点）；
4. **停止条件**：若 `P≥0.95` 下 R 增益 < 1.5 pt（约等于本轮 CI 下界的一半），
   则锚点降级为「离线回填 + 人工复核排序」，不进实时链路。

**前置依赖**：先确定人脸匹配阈值。当前 `--tau 0.45` 是在聚类场景调的，
放到选择器里会因为分母不同而失效——需要按 `same ≥ 0.98` 重新标一次工作点。
