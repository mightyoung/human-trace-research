# 姿态池里的「人脸识别到谁」：从真值换成实测（2026-11-13）

> 承接 `docs/mainline-pose-pool-2026-11-11.md`（56.4% → 68.2% → **79.3%**，上限 92.7%）。
> 该文档顶部自己写明：「人脸『识别到谁』用 GT 身份 → 这是**上限**」。
> 本文把这处换成**真实识别**，量出实际折损。
>
> 脚本 `tools/exp_pose_pool_real.py`；数据 8 段 / 445 具名轨 / 26 身份 / OSNet-x1.0；

## 0. 结论先行

| 口径 | recall@0.80 | 相对上一行 |
|---|---:|---:|
| S0 历史库均值 | 56.4% | — |
| S5 形态加权（不用人脸） | **68.2%** | +11.8 |
| S5 + 池（**身份用真值**，原口径） | **83.2%** | +15.0 |
| S5 + 池（**真实人脸识别**） | **69.8%** | **+1.6** |
| S0 + 池（身份用真值） | 79.3% | +22.9 over S0 |
| **S0 + 池（真实人脸识别）** | **61.5%** | **+5.1 over S0** |

1. **79.3% 复现无误**，但它确实是「身份全对」的上限。换成真实识别是 **61.5%**，**折损 17.8 pt**，
   22.9 pt 的池增益只剩 5.1 pt（回收 22%）。
2. **折损几乎全部来自覆盖率，不是认错人。** 三段分解（τ=0.80）：
   79.3 → 62.6（可用脸门，−16.7）→ 61.5（该身份有没有人脸原型，−1.1）→ 61.5（认错，**0.0**）。
3. **79.3% 这一行的标签原本就是错的**（本文顺带修正）：79.3 是「库均值 + 池」，
   不是「形态加权 + 池」。形态加权再叠池是 **83.2%**。原文档把它写成「68.2 → 79.3，人脸增量 +11.1」，
   把两个不同基线相减了。人脸在形态加权之上的真实增量是 **+1.6**（69.8 − 68.2），不是 +11.1。
4. **不用人脸的形态加权（68.2%）打败了用真实人脸的池（61.5%）。** 这是本文对产品最重要的一句。

## 1. 两个口径差在哪

原口径：`face_vecs_*.npz` 里有 `|full` 向量就算「这条轨有脸」。

实测口径：`face_track_*.csv` 的 `usable ≥ 1`，即至少一帧同时满足
`pd≥20 且 fw≥32 且 lap≥50 且 |yaw|≤0.35 且 0.25≤pitch≤0.95`。

| 口径 | 445 具名轨 | 全 8 段 1178 轨 |
|---|---:|---:|
| 有任意脸向量 | 141 = **31.7%** | — |
| **可用脸（质量门）** | **54 = 12.1%** | **77 = 6.5%** |

差的这 2.6 倍，正是「检到了脸」和「脸够大够正」的差别。可用率与 `mainline-face-bridge-count-2026-11-10.md`
的历史记录一致（该文记 77/1178 = 6.5%），不是本文新造的数。

**所以 79.3% 里那句「人脸覆盖 31.7%」本身就偏乐观**：真正能写进池的只有 12.1%。

## 2. 真实识别的做法（不看真值）

- **人脸库**：上午(train) 每「机位×身份」的可用脸均值作原型。
- **识别**：查询轨人脸对同机位原型取最近邻，需 `cos ≥ τ_face` 且领先次优 `≥ margin`，否则算「没认出」→ 不写池。
- **写池**：只写认出的那条身份；因果（打分之后才写），FIFO 容量 8，top-3 均值，同机位分层。
- 真值只用于**评测**识别对不对，不进机制。

### 人脸库只覆盖 9/48 个「机位×身份」

| 机位 | 候选身份 | 上午有可用脸原型 |
|---|---:|---:|
| 305 | 16 | **2** |
| 318 | 14 | **3** |
| 320 | 5 | **1** |
| 323 | 13 | **3** |
| 合计 | 48 | **9（18.8%）** |

这是最关键的一处：**81% 的身份根本没有可用来认脸的原型**。所以剩下的路径只有
「用该身份全部可用脸（含下午、留一）建原型」，覆盖也只到 15 组 —— 换来的识别精度提升为零（见下）。

## 3. 识别质量：20/20 全对，但这是平凡任务，不能当成「人脸很强」

| 口径 | 有库 | 认出 | 认对 | 精度 |
|---|---:|---:|---:|---:|
| 只用上午原型 | 18 | 18 | 18 | **100%** |
| 库补齐（留一，含下午） | 20 | 20 | 20 | **100%** |

必须把括号里的限制一起报，否则会误导：

| 量 | 值 |
|---|---|
| 候选身份数 | **2–6（中位 3）** |
| 正确身份余弦 | 0.453 – 0.903 |
| 最优错身份余弦 | 0.008 – 0.387 |
| 间隔（正确 − 最优错） | 中位 **+0.647**，最小 +0.285 |

**2–6 选 1、间隔中位 0.65，100% 是必然结果，不能推出「人脸识别可用了」。**
同一个项目里把候选扩到约 50 个时，实测 1:N rank-1 只有 **50%**（`face_1n.json`）。
两个数不矛盾：一个是 3 选 1，一个是 50 选 1。

→ 正确表述是：**在这份数据里，识别精度没有成为瓶颈，是因为难的那些查询在「有没有人脸原型」这一步就被筛掉了，根本没进识别环节。** 一旦人脸库补齐到 48 个身份，识别精度会重新成为约束。

τ=0.80，recall，分母 179（本人上午在该机位有库）。括号内为判对条数。

## 5. 顺带修正：79.3% 与 68.2% 不是同一条链上的两步

原文档 §3 的表把 `S0 / S4 / S5 / S1` 放在同一行，正文写「人脸的增量是 +11.1 pt（68.2 → 79.3）」。
但代码里：

```python
s1 = {p: max(libsc[p], poolsc[p]) for p in cands}   # libsc = 库均值，不含形态加权
s5 = ...                                             # 形态加权，不含池
```

即 **S1 = 库均值 + 池（79.3）**，**S5 = 形态加权（68.2）**，两者基线不同，不能相减。
把池叠在形态加权上才是真正的「两个机制叠加」：**83.2%**。

所以正确的阶梯是：

```
56.4  ──形态加权──▶  68.2  ──池(身份全对)──▶  83.2  ──身份换真实识别──▶  69.8
```

- 人脸在形态加权之上的**上限**增量是 +15.0（不是 +11.1）；
- 真实增量是 **+1.6**。
- 论文 `docs/paper/main.md` Table VI（第 318–320 行）沿用了这个错标，把 79.3 记成
  「+11.1 over S1」，需要一并修正。

## 6. 该做什么

1. **别再把 79.3% 当可交付收益。** 真实识别下同口径是 **61.5%**；在有意义的叠加口径下，
   形态加权 68.2% → 加真实人脸池 **69.8%**（+1.6）。
2. **要动这个数只能动采集**：可用脸 12.1%、身份级人脸原型 18.8%。
   根因仍是 `pd/box_h ≈ 0.054`（`mainline-face-anchor-2026-11-10.md` §2.1）。
3. **产品上优先做形态加权，不是人脸池。** 它零训练、零人脸、+11.8，且不依赖采集。
4. 若要继续验证人脸池，需要的是**同一身份在不同形态下的可用脸**，不是更多轨。
