# fp32 一致性与重跑复现性核查（2026-10-19）

问题：之前用的 fp32，和本机跑的一致吗？

## 0. 结论

| 环节 | 精度 | 本机重跑 vs 存档 | 判定 |
|---|---|---|---|
| OSNet 表征（CPU） | **fp32** | **逐位相同**（91/91 键，最大分量差 0.00e+00） | 完全一致 |
| OSNet 表征（DirectML） | fp32（DML 内核重排） | 最大分量差 7e-7，cos ≥0.9999999 | 等价，0 条判决翻转 |
| 人脸 SCRFD/ArcFace（cv2.dnn CPU） | **fp32** | 三个进程输出逐位相同 | 完全一致 |
| YOLO 检测（CPU） | **fp32**（无 half/amp） | 同参数两次 40/40 逐位相同 | **确定性没问题** |
| 存档检测文件 | fp32 | **只有 iou 0.7 + 去重 这条路径能逐位复现**；现在的默认 iou 0.5 不能 | **配置漂移，见 §4** |

全链路没有任何 fp16 / amp / bf16：`encode_1012_osnet_seq.py`、`yolo_track_det.py`、`probe_face_routing.py`
里检索 `half|float16|amp|bf16` 命中 0 处；YOLO 显式 `device="cpu"`；`cv2.dnn.readNetFromONNX` 未设
`DNN_TARGET_OPENCL_FP16`，走默认 CPU fp32。

## 1. OSNet：逐位可复现

重跑 `305_test_544`（91 条轨迹 × 2 份 a/b）到临时目录，与 `1012_yolo8_dd_emb` 存档比对：

| 设备 | 共同键 | cosine 最小 | 最大分量差 | 逐位相同 |
|---|---|---|---|---|
| CPU | 91/91 | 0.9999999\* | **0.00e+00** | **91/91** |
| DML | 91/91 | 0.9999999 | 6.7e-07 | 0/91 |

\* cosine 略小于 1 是 float32 点积累加误差，向量本身逐位相同。

**结论：存档就是 CPU fp32 生成的**，本机重跑完全一致（91/91 精确相等）。

## 2. DirectML 的 7e-7 会不会改变判决

把 DML 重编码的 90 条 305_test 轨迹替换进生产打分链路（机位感知聚类、thr 1.85）：

| 检查 | 结果 |
|---|---|
| argmax 簇变化 | a 片 **0** 条，b 片 **0** 条 |
| 接受/拒识翻转 | **0** 条 |
| 分数最大变化 | a 4.5e-06 / b 7.6e-06 |
| 最靠近门槛的一条 | 距 1.85 有 **0.037** |

噪声比判决边界小 4 个数量级。**换设备不会改变任何结论。**

## 4. YOLO：确定性没问题，但**存档不是现在的默认参数跑出来的**

`305_test_544` 前 40 个采样帧（0–195 帧，stride 5）：

| 对比 | 完全一致的帧 | 框数 | 框几何 |
|---|---|---|---|
| 同参数跑两次（iou 0.5） | **40/40** | 336 = 336 | 逐位相同 |
| 存档 vs 本次 iou 0.5 | **8/40** | 336 = 336 | IoU≥0.5 的占 99.7%，≥0.9 的占 96.1% |
| 存档 vs 本次 iou 0.7 | 0/40 | 336 vs 376 | — |
| **存档 vs （iou 0.7 + dedup 0.5）** | **40/40** | 336 = 336 | **逐位相同** |

**结论：存档检测文件是 `iou=0.7` 跑完再 `dedup_detections --iou 0.5` 得到的，这条路径能逐位复现。**

而 `yolo_track_det.py` 的默认 iou 后来被改成了 0.5。用现在的默认重跑，**框集合几乎一样，但轨迹不同**：

```
存档 track_id -> 本次 track_id 的映射
  1→1(40帧)  2→2(40帧)  3→3  4→4  5→5  6→6  8→8
  7→10(19帧) 7(4帧)     ← 一个人在第 20 帧前后发生 ID 切换
  9→9(20帧)             ← 该轨迹只有一半帧能对上
```

40 个采样帧内出现 **1 次 ID 切换**。原因是 NMS 阈值不同 → 进入 ByteTrack 的框集合略有差异 →
某帧的关联判断翻转 → 轨迹分裂。`frame 0–15` 逐位相同，从 `frame 20` 开始出现位移（最大 37px）。

**影响**：轨迹是下游一切分析（a/b 分片、聚类、覆盖率）的输入。1 次 ID 切换在一个 40 帧窗口里出现，
说明两条路径**不等价**，不能当"同一份数据"混用。

## 5. 建议

1. **profile 的 pipeline 命令要显式写 `--iou 0.7`**
   （`configs/selector_deploy.json` 现在只写 `--stride 5|10`，照文档重跑会用到新默认 0.5，得到的检测与存档不一致）。
2. 若决定改用 0.5：需要重跑 8 段 + 重编码 + 重算基线，约 2h；在拿到新基线前，**不要把 0.5 的产物与现有指标混用**。
3. 存档产物（`1012_yolo8_dd*`、`1012_yolo8_dd_emb`）目前是唯一可信基线，且**可逐位复现**（走 0.7+dedup + CPU 编码）。
