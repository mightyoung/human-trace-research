# M1 启动审计：三个前置，一个必须先改的判据（2026-10-23）

> 目的：在动代码之前，先把 M1 的「输入、工具、判据」三件事核清楚。结论是——
> **工具不在本机，判据对 42% 的样本不可执行**，但观测日志够用，可以绕开工具先跑。

## 1 事实：三项前置审计

### 1.1 切轨迹工具不在本仓库

```
$ find . -iname "*tracklet*"        → 空
```
V0.4 写的「`tracklet_extract.py` v0.3.1……合成视频与 MOT17-04 已验证，现场未跑」，
在本仓库里**连文件都没有**。所以 M1 的真实阻塞不是「本机 Windows 没跑通」，而是**代码不在本机**。
（`audit_sample.py`、`motion_predictor.py` 同样不存在。）

### 1.2 依赖缺一个

| 依赖 | 状态 |
|---|---|
| `ultralytics` | ✅ 在 `pylibs/`（8.4.182），靠 `PYTHONPATH` 生效 |
| `torch 2.4.1+cpu` / `torchreid` / `lap` / `scipy` | ✅ |
| **`boxmot`** | ❌ **缺失**（BoxMOT 是 BoT-SORT / Deep OC-SORT / BoostTrack 的载体） |

即使拿到 `tracklet_extract.py`，还要 `pip install boxmot` 到一个离线目录；而 BoxMOT 会连带
拉 `ultralytics` 的另一版本，有和现有 8.4.182 冲突的风险——需要在 `pylibs` 里做隔离安装并验证。

### 1.3 ★ 判据问题：`id_switch_frame` 有 42% 是轨迹末帧

46 条串人成员里，切换帧字段的实际质量：

| 情况 | 条数 |
|---|---:|
| 可解析为帧号 | **45 / 46** |
| 其中 **恰好等于该轨迹的末帧**（`t_end_frame`） | **19** |
| 多切点（逗号分隔，如 `44730,44780`） | 4 |
| 非数字（自由文本，如「change to female8」） | 1 |
| 距起点 ≤5 帧 | **0** |

也就是说，**没有任何一条的切换帧落在轨迹开头**，而有 19 条正好落在结尾。
这不是真实交错点，是标注时被自动填成「当前帧/末帧」的痕迹。

**后果：M1 原定判据「切点落在 `id_switch_frame` ±1s 内 → 判为已拆开」对 19/45（42%）条不可执行**——
在那个帧上切开等于在轨迹末尾切，只会得到一个空片段。**这个门槛现在不能签。**

## 2 好消息：观测日志足够，可以零推理做切分

`output_crosscam_local/1012_yolo8_dd/{seg}/{seg}_detections.jsonl` 逐帧保存：

```json
{"frame": 0, "track_ids": [1,2,...], "boxes": [[x1,y1,x2,y2],...], "scores": [...]}
```

这意味着 4.1 节里的大部分规则**不需要重新推理**，可以作为后处理跑：

| V0.4 §4.1 规则 | 能否用现有日志实现 | 缺什么 |
|---|---|---|
| 他人框 IoU ≥ 0.30 只记「重叠」 | ✅ 框都在 | — |
| 重叠结束后比较前后 1 秒的相对位置，顺序互换超 15% 才切 | ✅ | — |
| 前后缺对照（一方消失）保守切断 | ✅ | — |
| 轨迹断开 > 1 秒切 | ✅ | — |
| 单框多人（尺寸突增 1.5×） | ✅ | — |
| **掩码重叠 ≥ 15%** | ❌ | 日志只存框，没有掩码 |
| **轨迹内外观突变切分** | ❌ | 没有逐帧 ReID 向量（npz 是每轨 8 帧） |

按 V0.4 自己的结论「重叠切分是纯度的主力，外观切分只是补充」，缺的两条不阻断第一轮验证。

## 3 建议：把 M1 判据换成「结果侧」，先跑得动再谈 80%

三个选项：

| 方案 | 判据 | 成本 | 风险 |
|---|---|---|---|
| **A 补标切点** | 重填 19 条末帧 + 4 条多切点 → 原 ±1s 判据成立 | 人工约 20 分钟 | 需要看 8 帧拼图定位，精度有限 |
| **B 结果侧（推荐）** | 每轨被切成 ≥2 段、**两段各 ≥2 秒**，再人工抽检 20 条确认两段确实不同人 | 自动 + 抽检 20 条 | 判据不含"切点对不对"，只含"有没有切出两个有效人" |
| C 只看下游 | 不问拆开率，只看保留率 >65.6% 且精度 ≥0.95 且 C/229 ≥0.511 | 自动 | 无法归因：可能是切分有效，也可能是别的改动 |

**推荐 B + A 的合并**：先按 B 自动跑全量（不需要人），只把 19 条末帧的用 A 补标，
这样"拆开率"与"切点准确性"两件事分开报告，80% 才有意义。**这一条需要 @Haro 确认。**

## 5 本机下一步（不等工具）

**R2（交错感知，V0.4 称之为"纯度的主力"）只触发 2 次**，说明我的重叠事件簿记有 bug：
当前实现用一个全局帧表遍历、一旦任一方在该帧缺失就跳过，导致绝大多数重叠事件被记成
"R3 消失"或直接漏掉。这不是参数问题，是实现问题。

**对 46 条的覆盖（323 的 27 条串人轨迹）**：

| 情况 | 条数 |
|---|---:|
| 切换帧是末帧 / 不可解析（判据失效，见 §1.3） | 10 |
| 切点命中 ±1s | **3** |
| 有切点但位置不符 | 12 |
| 完全没切 | 2 |

即可评估的 17 条里命中 **3 条（17.6%）**，离 80% 很远。

**结论（不许含糊）**：照搬 V0.4 的参数与规则，在 1012 上既切不准也太碎。
下一步必须先修 R2 的事件辨识，再按"碎片率 ≤1.5 倍、过短率 ≤30%"重标定参数，
最后才谈 80%。**在修好之前，M1 的进度不能报"已启动"，只能报"原型验证失败，已定位原因"。**

## 7 A 方案已就绪：46 条换人时刻复核页（带跟踪框，约 20–25 分钟人工）

按「先 A 后 B」执行。产物：`deliverable/data-request-v2/gt/switch_review.html` + `gt/clips/*.mp4`。

**为什么必须带框**：第一版只放原视频，打开后看不到跟踪框——而「串人」这件事恰恰只能通过
**框在哪一刻跳到另一个人身上**看出来。没有框，人眼无法判断该记哪一帧。

**为什么不用拼图**：8 帧拼图在 5000 帧的轨迹上间隔约 700 帧（28 秒），定位不到 ±1 秒；
而且现有拼图的「第几张 ↔ 第几帧」映射没有留档，用它当证据等于猜。

**片段规格**（`tools/render_switch_clips.py`，supervision 画框 + ffmpeg libx264 编码）：

| 片段 | 区间 | 帧率 | 宽度 | 用途 |
|---|---|---|---|---|
| `focus` | 原记录点 ±8s（原记录为末帧/不可解析时取轨迹末 20s） | 原生 25fps | 1280 | 定位到 ±1 秒 |
| `scan` | 整条轨迹 `[t_start−1s, t_end+1s]` | 5fps 抽样（**时长与真实一致**） | 768 | 快速扫完全程 |

画面上：绿粗框＝该轨迹（带 `TARGET <tid>`）、灰细框＝同场其他人（近场标 `#tid`）、
右上角放大镜（远处目标只有几十像素，不放大看不出是谁）、左上帧号/秒数、底部时间轴
（灰段＝本片段、黄刻度 `rec`＝原记录点、绿点＝当前）。

**操作（4 步）**：

```bash
# 0) 先算窗口、再渲染片段（46 条 × 2 段，实测 9 分钟，94 MB）
PY tools/switch_windows.py
PY tools/render_switch_clips.py      # 只补某几条：--only "323_train_510#3169,318_train_525#1041"

# 1) 起一个带 Range 的静态服务（必须——普通 http.server 不支持 seek，视频会从头播）
PY tools/serve_range.py --dir D:/human-count --port 8903

# 2) 浏览器打开
#    http://127.0.0.1:8903/deliverable/data-request-v2/gt/switch_review.html

# 3) 逐条：空格播放/暂停 · ←/→ 微调 0.5s · Enter 记录 · Tab 下一条
#    「聚焦片段 / 全轨迹扫描」两个视图可切换，切换时保持同一真实时刻
#    46 条，约 20–25 分钟；进度自动存本地，中断可续

# 4) 点「导出 CSV」，然后并回台账
PY tools/ingest_switch_review.py --csv C:/Users/xxx/Downloads/a3_switch_review_FILLED.csv
```

**依赖**（已装进 `dml_torch` 环境）：`supervision==0.24.0`（0.31 依赖的 `deprecate>=1.2` 在本机镜像里没有）、
`imageio-ffmpeg`（只用它自带的 ffmpeg 7.1，带 libx264；OpenCV 的 `mp4v` 浏览器不放）。

**窗口覆盖兜底**：46 条里有 25 条原记录不可用（末帧/越界/无法解析），默认取轨迹末 20s；
若该窗口内目标检测覆盖率 < 30%，自动滑到检测最密的一段（本次命中 2 条：`323_train_510#3169`、`318_train_525#1041`）。
仍有 6 条覆盖率 < 40%——这些轨迹本身只有 7–49 个检测点，属于"框时有时无"，
页面会显式提示并允许按 `X` 标「无法判定」，不强迫标注人猜。

**导出的 `switch_frame` 口径**：一律是 ledger 的 25fps 帧号（`片段起始帧 + currentTime×25`），
不依赖容器时长。实测容器 90151 帧 / 3600s 有约 0.17% 漂移，因此**按帧定位，不按秒定位**。

**`ingest_switch_review.py` 的校验规则**：切点必须落在 `[t_start+2s, t_end−2s]` 内，
贴边一律判无效——否则"切开"只得到一个空片段。输出 `results/switch_valid.json` 供 M1 判据直接读，
并打印「可用 / 贴边被拒 / 未填」三个数。
